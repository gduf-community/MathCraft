# Agent 出题优化方案

第一阶段代码已接入。目标分支为 `codex/agent-question-quality`，基于 `agent`。第二至第四阶段待推进，依次为 Phoenix 本地追踪、教师标定样题验证和 SDK 重构评估。

2026 年 11 月 22 日的数学分析实测中，六种题型各请求四档各一题，首轮交付 18/24 道，补跑后交付 23/24 道。低档多选缺少可作答的数学命题却被交付，高档简答要求证明的结论被解析中的反例推翻，地狱档简答多次缺额。部分高档和地狱档题目用常规解法即可完成。这四类现象分别作为交付、纠错、缺额排查和难度评估的验收依据。

## 一、修复出题、纠错和交付流程

适用于对话出题和参数化出题。两种入口使用同样的题目验收条件和补题预算。

1. **设置交付硬条件。** 数学可解性、题面完整性和指定范围必须通过验收。指定范围同时约束题目考点和成品解析所用方法。按请求档位交付，难度不符的候选进入修补或换题。
2. **结构化记录独立求解判定。** 区分正常作答、题设不足、待证命题为假、条件矛盾和无法验证。判断题判错并给出反例可以是正常作答。证明题要求证明为真的命题一旦被反例推翻，应判为题干缺陷。模型调用失败、结果无法解析或验证证据不足时，记录为无法验证。
3. **带证据修题并重新验收。** 将反例、缺失条件或矛盾条件交给修题步骤。每道候选最多定向修补一次，仍未通过则换题。修订后从完整题面重新审查。原题模式下，若修订会改变原题的数学含义，优先换另一道材料原题。
4. **联合验收成品。** 对最终题干、选项、答案和解析一起检查。选择题核对各选项的定义域、真假、正确项数量及其与答案的对应关系。证明题核对解析是否完成题目要求。要求指定范围内的解法时，先尝试改写超出范围的解析，改写后仍需验收。
5. **统一补题预算。** 首轮生成后，整个请求最多再补三轮。各题型和档位共用预算，每轮只补实际缺额，新候选经过同一条验收链。达到配额或预算耗尽时结束。
6. **向教师输出结果。** 按题型和目标档位给出请求数、交付数、缺额及主要拦截原因，覆盖足量交付、部分交付和零交付。原因由程序根据实际判定汇总。拦截原因的计数单位是候选题，与最终缺额分开显示。

**验收**。复用本次实测的无效多选、错误证明题和越界选项案例。验证被否决的题无法补位，有反例的证明题进入修题或被剔除，修后成品重新验收。构造连续失败的批次，确认首轮后最多补三轮，教师得到与实际交付一致的缺额和原因。

**实施状态**。同步参数化、后台参数化和对话出题共用编排，首轮后共享最多三轮补题。后台任务的 `review.groups` 为可选分组明细。同步调用传入 `include_review=true` 时返回含 `questions` 和 `review` 的对象，默认仍返回题目数组。对话助手消息展示交付摘要。首轮原题不足沿用来源确认，补题失败记入分组生成事件，取消沿用现有停止机制。具体字段、异常边界和验收见 [出题审核中间件设计与实施记录](../design/出题审核中间件设计与实施记录.md#第一阶段交付设计)。

## 二、补充 Phoenix 埋点并做本地出题测试

**由 MathCraft 判定每道候选题为何被拦下，Phoenix 展示这次判定发生在哪一轮、哪个环节，以及关联模型调用的状态。**

- 当前分支只上报运行和模型调用元数据，逐题审核结果与缺额原因仍待接入。沿用 `run_id` 关联业务运行，补充候选标识、题型、目标档位、补题轮次、阶段、审核结论和原因码。命题、求解、修题、复审、成品验收及补题阶段应能与对应模型调用关联。运行结束时记录按题型和档位汇总的缺额。保持现有元数据采集边界，题目正文、反例、提示词及答案正文留在 MathCraft 的业务流程。 [当前 Phoenix 接入说明](../design/Phoenix可选扩展.md)
- 按 Arize Phoenix 官方文档，使用自托管 Docker 和 OpenTelemetry 自定义 span、属性与筛选能力。沿用现有 Compose 的固定镜像和本机端口 `127.0.0.1:6017`，通过 `/v1/traces` 接收追踪。教师反馈与运行台账以 MathCraft 的实际交付结果为准。追踪导出可能缺失，验收时应从 Phoenix 实际读回记录。 [仓库部署配置](../../compose.phoenix.yaml) · [Phoenix Docker 部署](https://arize.com/docs/phoenix/self-hosting/deployment-options/docker) · [自定义埋点](https://arize.com/docs/phoenix/tracing/how-to-tracing/setup-tracing/instrument) · [按属性筛选](https://arize.com/docs/phoenix/tracing/how-to-tracing/filter-expressions)

**验收**。在本机启动 Phoenix，跑通正常交付和触发缺额的出题任务。按同一 `run_id` 核对 Phoenix 逐题记录与 MathCraft 的教师输出。用模型超时和 HTTP 200 但发现反例这两种情况，验证能够区分调用故障与业务验收失败。优先复测此前多次缺额的地狱档简答，核对求解、修题和补题的实际结果。

## 三、接入教师标定样题并验证难度区分度

教师标定样题是教师明确指定难度档、可用于校准新题难度的题库例题。首版方案建议由教师从有权限访问的题库中选题，记录题型、考点、难度档和标定理由。

- 将教师标定样题加入出题参考 Skill，对话出题和参数化出题共用。优先匹配同题型、同考点、目标档位的样题。有相邻档样题时并列对照。缺少合适样题时使用现有难度规则。
- 命题阶段用样题的关键定理、推理步骤和最短合理解法约束命题蓝图。成品完成后先独立解题，再对照样题校准难度。题目仍须通过第一阶段的交付条件。
- 固定教材范围、题型、目标档位和模型配置，分别运行启用样题和未启用样题的批次，每个题型及档位使用多道题。由不知道试验分组的复核者独立评定成品的实际难度，比较目标档命中率、高档与地狱档的混淆率，同时记录正确性和交付率。

**验收**。交付两组对照结果和样本量，说明样题对各题型的难度区分是否有改善，并记录正确性、交付率的变化。

## 四、评估是否迁移到 OpenAI Agents SDK

基于前三阶段的实测，评估当前出题编排在阶段依赖、并发、取消、重试、结构化输出和追踪方面的维护成本。若 SDK 有望降低复杂度，先用「独立求解 → 成品验收」验证，复用无效多选、错误证明题和缺额回归样本。比较现有模型端点的兼容性、运行结果和接入后的代码复杂度，并核对补题预算、交付判定、取消和落库行为。

**验收**。形成有对照证据的架构决定，明确继续沿用现有实现或迁移哪些环节，以及相应收益和成本。是否扩大到其他 Agent 模式由验证结果决定。
