每题使用 `question_id` 与非空最终 `content_revision` 匹配证据；`run.revision` 是运行摘要版本，`final_content_revision` 是集合版本，均不能替代每题版本。匹配当前版本的 `passed/failed` 只计实际完成范围；明确通过范围还需该范围证据一致通过。`skipped/unknown`、冲突或旧版本证据不能冒充当前版本通过。逐条证据保留并标明当前版本、旧版本或关联未知，缺证据不算明确跳审，不自动触发模型复审。服务端质量计数仍由 M3 冻结口径提供，前端不重算业务终态。

原六条已知规则外新增 `monitoring_pipeline_failure`、`capacity_warning`、`notification_failure`。`opsKnownAlertRules` 仅用于已知标签及筛选；`OpsAlertRule` 保持 `string`，响应边界只接受匹配 `^[a-z][a-z0-9_]{0,99}$` 的安全标识。未来未知规则保留原始 ID 和通用指引，不拒绝整页、不猜测阈值或恢复条件；后端允许的筛选规则集合仍待 G1 冻结。

自监控区三按钮仅携带上述对应 `rule_id` 进入异常中心，沿用默认近 24 小时 `first_seen_at` 新建轮次窗口，不等同全部活动故障。指标缺省／null／过期均不展示健康。解析器只做时间结构和 `fresh_until > observed_at` 的结构校验，不读取客户端 `Date.now()` 改写状态；`useOpsClock` 以服务端 `generated_at` 加页面经过时间持续复核新鲜度，过期时由 UI 展示 unknown。依赖面板顶层保留时钟，来源筛选重挂卡片不能延长有效期，自监控也复核 `observed_at/fresh_until`，失败轮询不延寿。

时钟的经过时间单调累加 `max(wallDelta, performanceDelta, 0)`，处理系统校时回拨和 Windows 休眠；客户端墙钟只参与经过时间差，不能替代服务端快照作为绝对证据时间。新快照只向前校准，旧快照或空数据不能回拨；概览将时钟提升到父层，依赖时钟也位于面板顶层，过滤或展示区重挂不重新起算。对 `observed_at > generated_at`（依赖使用 `checked_at`）的未来观测，UI 在该快照内始终显示 unknown，不随经过时间增长变成 healthy；只有更新的有效快照才能重新判断。解析器仍保留服务端原始状态，不按本机绝对时间覆写。

真实 `openTrace` 固定异步返回 `not_integrated`，关闭正文访问，不因 `available` 或安全 `viewer_path` 存在而跳转，也不请求尚不存在的授权／审计端点。DEV 保留原五种页面场景，另增 `trace_denied→denied`、`trace_audit_failed→audit_failed`、`trace_expired→expired`、`trace_simulated_success→simulated_success` 四种访问演示；模拟成功也只反馈合成结果，不打开正文、不形成真实审计。未来真实访问须满足独立权限、打开前到期复核及审计成功，并另行冻结接入契约。

本次还覆盖分页追加后暂停、刷新第一页失败保留集合与暂停状态、成功后恢复首屏刷新；通知操作与轮询竞争、筛选清除及焦点遍历／归还。本次新增检查已执行，结果见[升级方案第 10.3 节](运维后台升级方案.md#103-2026-11-12-补全检查)，2026-11-11 验收不覆盖这些新增项。

## 2. 现有实现衔接与共同约定

### 2.1 权限、错误与数据边界

定向只读核对依据：`backend/app/deps.py` 的 `require_admin`、`backend/app/errors.py` 的 `AppError`、`backend/app/main.py` 的异常处理，以及 `schemas/admin.py`、`schemas/api.py`、`schemas/notifications.py`。

- 五个新增接口全部沿用现有登录验证和 `Depends(require_admin)`，不增加第二套管理员身份。教师、学生被拒绝；账号禁用、令牌失效继续走既有认证链路。管理员运维摘要权限不扩大为教学资源读写权限。
- 成功响应不套用错误结构；错误继续为 `{"detail":{"code":"...","message":"..."}}`，固定中文安全文案，不回显输入、底层异常、连接串或正文。沿用 `Cache-Control: no-store`；422 沿用现有 `VALIDATION_ERROR`。
- 运维响应只允许标识、时间、计数、枚举、预定义原因码、安全文案及明确允许的非敏感生效阈值、单位、窗口与配置来源摘要；不包含提示词、对话、题干、答案、检索片段、模型／工具请求响应正文、个人配置、凭据、Cookie、认证头或原始异常。`owner_user_id` 是内部账号标识，前端需要姓名时沿用现有账号管理能力，不复制个人配置。
- 详细对话及出题相关 API 正文只进入 Phoenix；使用字段白名单和递归脱敏，排除登录、认证、个人模型设置等敏感接口。正文、URL、属性、异常、工具参数均在进入导出缓冲前脱敏，不能仅屏蔽 HTTP 头。运维库不复制正文。
- 本地 Phoenix 单独实施访问控制，不把 MathCraft 管理员身份自动当作 Phoenix 授权，不在跳转地址附加访问令牌。未经授权不返回可用正文链接。

现有 `PlatformOverview.task_scope="persisted_generation_batches"` 及其最近 50 个批次仍按原语义使用；新增 ops 概览使用独立 `sdk_agent_runs_v1` 范围。禁止将批次数量或成功落库记录当成全部出题请求、失败率分母。

### 2.2 时间、空值和一致性

| 项目 | v1 约定 |
| --- | --- |
| 时间格式 | 所有时间为 RFC 3339 UTC，带 `Z`；界面转换本地时区。持续时间统一整数毫秒，比例为 0～1 的数值 |
| 时钟 | 业务事件使用服务端时间，心跳新鲜度使用服务端收到时间；不接受浏览器时间作为状态证据 |
| 时间窗口 | `from` 包含、`to` 不包含，即 `[from,to)`；不传时为服务端当前时刻前 24 小时，最大跨度 14 天，禁止未来时间及反向窗口 |
| 空值 | 未采集、证据不足、尚未产生用 `null` 或显式 `unknown`，并提供原因；只有实际观测到的零才返回 `0`。布尔值未知用 `null`，不能替换为 `false` |
| 空数组 | `[]` 只表示已确认集合为空；集合未知用 `null`。例如已确认无降级为 `[]`，未采集降级为 `null` |
| 记录版本 | 每个 run 的 `revision` 从 1 递增；事件具有内部幂等标识，重放不重复计数。并发、迟到事件不得覆盖更新版本或把已确认终态倒退为运行中 |
| 数据新鲜度 | 响应提供 `generated_at`；运行另有 `updated_at`，依赖及 trace 另有观测时间。HTTP 200 不证明所有子系统数据新鲜 |

所有成功响应共有 `schema_version:"v1"`、`generated_at`、`data_state:complete|partial`、`warnings:[{code,message}]`。无警告为 `[]`；`data_state=partial` 表示仍可返回的摘要存在缺口，字段按各自未知规则返回。主摘要存储完全不可读时返回 503，不伪装成空列表或全零概览；Phoenix 不可用不导致可读摘要接口整体失败。

## 3. 运行标识、生命周期与采集

### 3.1 关联基线

| 字段 | 类型与含义 |
| --- | --- |
| `run_id` | 不透明字符串；每次受理的出题执行唯一，在实际开始之前分配，失败也保留；不能等批次落库后才创建 |
| `owner_user_id` | 发起账号 ID；受理时固定，后续从已绑定上下文传递，不从并发全局变量取值 |
| `entrypoint` | `parameterized\|conversation`；后续入口需要显式扩展 schema |
| `session_id` | `string\|null`；对话关联现有会话 ID，参数化为 `null`。一个会话可对应多次 run；普通闲聊／槽位收集不自动算出题 run |
| `batch_id` | `string\|null`；v1 一次 run 对应零或一个持久化成果批次，在事务提交后绑定。失败可无批次，存在批次也不证明执行完成或质量达标 |
| `trace.sdk_trace_id` | `string\|null`；一次 run 对应一个 SDK 根 trace，内部工具及重出尝试作为子 span。已受理尚未创建 trace 时为空 |
| `trace.phoenix_trace_id` | `string\|null`；经导出适配确认的 Phoenix 标识；不得假定与 SDK 标识同格式或简单拼接生成 |
| `trace.group_id` | `string\|null`；有会话时使用 `session_id`，否则使用 `run_id`；是分组标识，不是单次执行标识 |

运行中的重出、修补和模型传输重试属于原 run；用户另一次发起执行分配新 run。trace 元数据仅附加 `run_id`、脱敏后的归属标识、`entrypoint` 和必要会话分组；平台通过上述映射定位，不依赖抓取 Phoenix 页面。跨线程、异步任务及并行工具显式传递上下文，两账号不得共享当前 run／trace 的可变全局状态。

所有绑定可为空，但应区分“尚未产生”与“未采集”：`collection_state=complete|partial|not_collected|unknown` 描述运行摘要采集覆盖；`unknown_fields:string[]` 列出本应有但缺失的字段路径，例如 `counts.actual_count`。合法的 `session_id=null`、开始前 `started_at=null` 不属于缺失。历史批次不自动补造 run；将来若提供历史摘要，必须标记 `not_collected` 并排除各项未知指标。

### 3.2 执行、观察与阶段

`execution_status`：`accepted|running|completed|failed|cancelled|unknown`。

- `accepted` 为受理成功、执行体尚未开始；`running` 必须有执行体开始证据；`completed` 为执行体确认正常结束，不承诺题量、审核或数学质量。
- `failed` 必须有明确失败事件；`cancelled` 必须有执行体确认停止，不能根据取消请求已受理推断。`unknown` 用于无法判断，不能当作失败或已结束。
- `execution_reason_code` 为 `MODEL_CALL_FAILED|TOOL_FAILED|DEPENDENCY_FAILED|PERSIST_FAILED|USER_CANCELLED|INTERNAL_ERROR|UNKNOWN|null`；无异常时为 null，已有失败但无法安全分类时为 UNKNOWN，不返回底层异常字符串。
- 正常迁移为 `accepted→running→completed/failed/cancelled`；开始前明确失败或取消可直接进入对应终态。首次恢复采集可由 `unknown` 按证据定位状态。终态修正只能由同一次执行的权威事件和更高版本完成，记录安全原因；监测器不合成业务终态。
- `accepted_at` 必填；`started_at`、`finished_at`、`heartbeat_at`、`updated_at` 按证据记录。三个终态的 `finished_at` 必须已知，否则标记采集缺失。进程重启、Redis TTL 到期、锁超时和 trace 缺失都不产生终态。
- `wait_ms=started_at-accepted_at`，开始前为 `null`；`elapsed_ms=finished_at-started_at`，非终态或缺任一时间为 `null`。运行中展示 `running_age_ms=generated_at-started_at`，不能冒充最终耗时。

执行体独立于模型调用每 15 秒发送心跳，记录服务端 `heartbeat_at`，不能只在阶段切换时更新；监测器每 15 秒评估。配置项允许调整上述间隔。`observation_flags` 为已确认命中的 `waiting_suspected|long_running_suspected|heartbeat_stale` 集合，无法评估时为 `null`，并给出 `observation_checked_at` 与 `observation_unknown_reason`。空集合代表最近一次有效评估未命中，不代表执行成功。

观察结果超过两个评估周期未更新时，observation_flags 返回 null、observation_unknown_reason=OBSERVER_STALE；不能把监测器失联解释为运行恢复。运行心跳与监测器评估新鲜度分别判断。

`current_stage` 为 `queued|preparing|retrieval|generation|review|repair|persisting|finalizing|unknown`。详情返回 `stages`：每项含 `stage_id`、`parent_stage_id|null`、`name`（同阶段枚举，不含 queued）、`attempt_index`（从 1 开始）、`status:running|completed|failed|skipped|unknown`、`started_at|null`、`finished_at|null`、`elapsed_ms|null`、`reason_code|null`。同一阶段可多次、可并行，不能将各阶段耗时相加当作运行墙钟耗时；结束后的 `current_stage` 保留最后已知阶段。未采集时间线为 `null`，不能伪造完整链路。

### 3.3 采集接点与事件生产契约（2026-11-12 确认）

以下为 SDK Agent 接入后的待实现契约，不表示当前代码已经发出这些事件。事实由拥有该业务动作的步骤产生，M2／M3／M4 消费；不能通过进度文案、HTTP 200、Redis 状态或批次存在反推。G0 使用验收专用内存收集器验证事件与 trace 关联；G2 才落实运维 SQL 和持久幂等，不新增持久事件总线或承诺恰好一次投递。

公共信封拟包含 `event_schema_version,event_id,run_id,event_type,occurred_at`，时间由服务端产生；适用时携带 `stage_id,question_id,question_revision_id,attempt_id,sdk_trace_id,phoenix_trace_id`。首次受理固定账号与入口上下文，后续事件从绑定上下文取得归属。G1 冻结事件名称、必填条件、生产步骤及消费模块，不能直接将本节建议字段视为已部署 OpenAPI。`question_revision_id` 是题目内容版本，与运行摘要递增字段 `revision` 不同。

| 采集接点 | 权威生产步骤 | 最小事实与消费方 |
| --- | --- | --- |
| 受理出题 `run.accepted` | 必要校验后，确定接受实际出题的入口 | run、账号、入口、可空会话和目标题量；M2 建立运行，普通聊天／槽位追问不建 run |
| 实际开始 `run.started` | 执行体开始处理已受理出题 | 开始时间、run 与 trace 关联；M2 进入 running，异步登记不算开始 |
| 候选形成／内容变化 `question.revised` | 生成、修补、重出、答案或解析更新步骤 | run 内题目标识、版本标识、变更原因；M3 跟踪内容，同一题目 ID 不代表内容不变 |
| 审核结束／明确跳过 `review.recorded` | 实际审核步骤或显式跳过分支 | 被审版本、实际范围、结论、时间与跳过／未知原因；M3 记录审核证据 |
| 重出开始／结束 `regeneration.started/finished` | 每个逻辑重出尝试的执行边界 | 唯一 attempt、结果、返回数量及耗时；M3 去重计数，传输重试不另算尝试 |
| 降级决策 `degradation.selected` | 实际选择替代路径或未审放行的步骤 | 安全原因码、阶段、受影响题目／尝试；M3 保留降级事实 |
| 最终集合提交 `delivery.committed` | 保存成果的业务事务成功提交后 | 批次、准确的已保存题目及版本集合、实际题量；M2 绑定批次，M3 更新最终集合 |
| 对话关联提交 `conversation.linked` | 助手回复及批次关联事务成功提交后 | 会话、回复与批次关联；M2 单独记录，不以题目提交冒充回复保存成功 |
| 正常结束／失败／取消 `run.ended` | 有权确认执行状态的执行体 | 权威终态、安全原因、已提交批次；M2 保存，取消请求受理不等于停止 |
| 依赖调用结果 `dependency.observed` | 模型、检索、存储等真实调用边界 | 逻辑依赖、范围、时间、耗时及安全错误分类；M4 生成被动观测 |

事务边界必须准确：当前 `services/generation.py::persist_batch` 中的 `flush()` 不是提交点，应在 `commit()` 成功后确认成果。当前 `api/chat.py::send_message` 的成果保存与随后助手回复保存存在两次提交；第二次失败不能抹掉首次已提交的题目，也不能宣称回复关联已完成。HTTP 返回与客户端收到响应另有边界，不作为持久化证明。上述源码仅用于说明事实语义，后续 SDK 实现应映射等价接点，本轮不为旧链路补过渡采集。

运维 SQL 只存必要标识、计数、范围及安全结果；题干、答案、对话与调用正文按白名单进入 Phoenix。事件重复、乱序及采集失败的持久处理在 G1 冻结、G2 验证；未采集的事实保持 unknown，不能用后续成功掩盖缺口。

## 4. 交付质量与计数

质量对象 `quality.status=met|attention|not_evaluated|unknown`：`met` 仅表示可观测的交付规则达标，不代表数学内容正确；`attention` 表示至少一个已知题量、审核或降级问题；运行未结束且暂无已知异常为 `not_evaluated`；结束后无法证明规则全部满足为 `unknown`。已知问题优先显示 `attention`，同时保留其他未知项，不因缺字段抹除异常。执行完成且降级必须显示 `completed + attention`。

| 对象／字段 | 含义与不变量 |
| --- | --- |
| `counts.target_count:int\|null` | 此次执行确定的目标题量，确定后大于 0；未确定为 `null`，不能填 0 |
| `counts.actual_count:int\|null` | 当前已持久化、可交付的唯一最终题目数；去重后计数，不包含候选、废弃版本、模型返回但未提交的结果；采集完整且确无成果可为 0 |
| `counts.quantity_status` | `met\|shortfall\|unknown`；终态且目标、最终实际数均已知时比较 `actual>=target`；执行中不提前宣告不足。详情可同时展示目标和当前实际数 |
| `review.required:bool\|null` | 本次交付是否要求审核；未知不能视为不要求 |
| `review.eligible_count:int\|null` | 当前最终交付集合中应审核题数；首期要求审核时等于实际题数，不要求时为 0 |
| `review.covered_count:int\|null` | 上述集合中最终版本在本次全部要求范围均获得明确 pass／fail 审核结论的题数；仅部分范围有结论或 unknown 放行不算完整覆盖 |
| `review.passed_count:int\|null` | 已覆盖题目中本次全部要求范围均明确通过的题数，`0<=passed<=covered` |
| `review.skipped_count:int\|null` | 应审但明确跳过／降级放行的题数；未知放行若有明确跳过事件记此项，不能计入 covered |
| `review.unknown_count:int\|null` | 应审、未明确跳过且最终版本或要求范围证据不确定／不完整／尚未完成的题数；计数链完整时 covered、skipped、unknown 互斥且之和等于 eligible |
| `review.coverage_rate:float\|null` | `covered/eligible`；分母为 0 时为 `null`，`coverage_reason=not_required\|empty_output`；缺证据时为 `null`，原因为 `not_collected\|incomplete`；正常为 `coverage_reason=null` |
| `review.status` | `complete\|partial\|skipped\|not_required\|unknown`；分别为全部题目最终版本的全部要求范围均有结论、已知部分覆盖或部分跳过、明确全部跳过、明确无须审核、证据不足。输出为 0 且要求审核时为 unknown，不能叫 complete |
| `degradation.occurred:bool\|null` | 有明确降级事件为 true；采集覆盖完整且无事件为 false；否则 null |
| `degradation.reason_codes:string[]\|null` | 预定义原因，如 `RETRIEVAL_FALLBACK`、`REVIEW_UNAVAILABLE`、`UNREVIEWED_RELEASE`、`MODEL_FALLBACK`；不返回自由文本异常 |
| `regeneration.attempt_count:int\|null` | 实际启动的逻辑重出尝试数；每次以内部 attempt ID 去重。一次尝试处理一个重出任务；请求了多个任务分别计数；SDK／HTTP 传输重试不重复计数 |
| `regeneration.succeeded_count/failed_count/in_flight_count:int\|null` | 分别为重出任务成功、失败、未结束数；计数完整时三者之和等于 attempt_count。成功不代表题目最终被去重保留 |
| `regeneration.total_attempt_ms:int\|null` | 已结束重出尝试的耗时之和，可包含并行重叠；不是运行墙钟耗时。未采集为 null |

审核覆盖始终按“最终交付题目的最终版本及本次要求的审核范围”计算，重复审核只算一题，重出替换后重新计算覆盖。`skipped_count>0`、明确审核未通过仍交付、`quantity_status=shortfall` 或 `degradation.occurred=true` 任一成立即为 `attention`。`met` 要求终态正常完成、题量已知满足、无降级，并且应审最终版本在要求范围内全部明确通过，或明确不要求审核；审核证据未知时不得判 met。

### 4.1 题目版本与实际审核范围

最终交付集合以业务事务成功提交的题目及其版本为准。每次题干、选项、答案或解析发生内容变化，生产步骤必须标记新版本，保留变更原因；题目 ID 相同不能复用旧版本结论。审核证据绑定被审版本及实际覆盖范围，例如题干难度、题干缺陷、答案校验；本次要求的范围与实际完成的范围分别记录。旧证据保留用于排障，不能静默升级为新版本或其他范围的通过证据。

最终覆盖只计算对应版本与要求范围均有明确 pass／fail 的题目；passed 还要求相应结论通过。所需范围未定义、版本无法对应或证据不足时标 unknown／incomplete，不默认完整覆盖。明确跳过分支才进入 skipped；仅缺少证据，或审核后答案／解析又被更新，不自动算明确跳审。界面必须能辨认实际审核范围，题干难度通过不能显示为全面数学正确性审核通过。

当前审核实现只向判定步骤提供题干，修补可能保留原题 ID，审核后的求解仍可能覆盖答案／解析；现有未版本化摘要不能证明最终全部内容已审。首期不为凑齐覆盖率自动增加模型复审，复审属于 Agent 业务范围的另行决定。前端已按第 1.2 节实现可选 `review_versions`、每题最终内容版本与实际范围证据展示；版本采集／持久化及后端 schema 仍待实现，G1 须冻结这些字段与第 3.3 节事件版本标识的映射，再同步后端、OpenAPI 和前端，不能据展示宣称真实审核证据已采集。

### 4.2 重出统计

重出比例定义为“有重出尝试的运行数／已知 attempt_count 的运行数”，不是重出尝试数／目标题数；attempt_count 大于目标数不构成字段错误。旧 `regenerated` 是每次尝试去重后、后续评估前的候选数量之和，既不是尝试次数，也不是最终交付保留数；不得用于替代新计数。首期展示次数、比例、耗时；阈值未配置时为 `unconfigured`，后续提供生效值时按第 1.2 节可选 `regeneration_config` 只读展示，前端不自行判异常。DEV 合成阈值不证明真实配置已经校准。

## 5. 追踪导出与可查看状态

导出状态、单条 trace 可读状态与 Phoenix 服务健康是三个维度：

| 字段 | v1 枚举与语义 |
| --- | --- |
| `trace.export_status` | `not_started\|pending\|submitted\|failed\|dropped\|unknown`；submitted 只表示本地导出端点受理，不证明已持久化或全部 span 齐全；缓冲耗尽／重试耗尽按证据记 dropped |
| `trace.availability` | `available\|pending\|expired\|not_found\|unavailable\|forbidden\|not_collected\|unknown`，解释如下 |
| `trace.complete:bool\|null` | 根 trace 及预期结束 spans 是否已核对齐全；根已可读但子 span 缺失可为 false，无法核对为 null |
| `trace.verified_at:string\|null` | 最近一次按具体 Phoenix trace 标识查询并确认结果的时间，不是服务健康检查时间 |
| `trace.reason_code:string\|null` | 如 `WAITING_FOR_EXPORT`、`LOOKUP_UNAVAILABLE`、`RETENTION_ELAPSED`、`ACCESS_UNVERIFIED`，使用安全白名单 |
| `trace.expires_at:string\|null` | 详细数据的逻辑到期边界；SDK trace 创建时间加当前保留期，未知起点则未知 |
| `trace.viewer_path:string\|null` | 仅在 trace 可读、当前访问权限已确认且未到期时返回的本地 Phoenix 相对路径；由锁定版本的适配器生成，不拼接令牌，不接受用户传入跳转地址 |

- `available`：本地 Phoenix 按映射 ID 的读取接口确实查到该根记录，并且当前访问授权已确认。只有 exporter 回调、HTTP 受理成功或 Phoenix `healthy` 均不足以证明该条 trace 可查。此状态证明查询时可读，不宣称数据库 fsync／备份保证。
- `pending`：已知仍在执行、导出队列或有界导出重试／索引可见性等待期内；默认结束后最多等待 60 秒，可配置。超过等待期不能一直假装 pending。
- `not_found`：有映射 ID、未到期、查询成功但查无记录，且已超过等待期。缺少映射或查询失败不能返回 not_found。
- `unavailable`：有明确查询通道故障；`forbidden`：明确被权限拒绝；`unknown`：缺映射、未核验权限、未能取得有效单条证据等；`not_collected`：明确未启用该次采集。权限未知时禁止返回 available 或可用正文链接。
- `expired`：有到期时间且已过逻辑保留边界，或有可信清理记录；不会因一次 404 就推断过期。到期后即便物理清理尚未运行也关闭正文入口。权限检查优先，不能通过到期状态向无权者泄露正文存在性。
- 单条可读证据默认有效 60 秒，可配置；过期未复核返回 unknown，若有新的连接故障证据则 unavailable。不得把旧 available 无期限缓存。查到根但 spans 不齐时 available 与 `complete=false` 同时展示“部分追踪”。

导出使用独立、有界、后台缓冲及重试；失败只影响追踪维度，不阻塞出题响应、不更改执行或质量终态，不在出题请求内无限重试或等待 flush。采集／导出异常按安全原因计数。运行摘要写入失败时保留业务原有执行结果，不因运维失败伪造业务失败；接口反映采集缺口，故障恢复后不得凭空回填未观测值。

接入配置须在首条 trace 前替换默认处理器链，确保只有本地出口；不能简单追加本地处理器后保留默认云端导出。具体 SDK、适配器和 Phoenix 版本在接入阶段锁定并验证，不在本文承诺某一版本已兼容。技术核对入口：[OpenAI 官方可观测性文档](https://developers.openai.com/api/docs/guides/agents/integrations-observability)；本文的具体状态机与保留期属于 MathCraft v1 设计决定。

`RunSummary` 精确包含：`run_id,owner_user_id,entrypoint,session_id,batch_id,revision,collection_state,unknown_fields,execution_status,execution_reason_code,accepted_at,started_at,finished_at,heartbeat_at,updated_at,wait_ms,elapsed_ms,running_age_ms,current_stage,observation_flags,observation_checked_at,observation_unknown_reason,counts,review,quality,degradation,regeneration,trace`。`quality` 另含 `reason_codes:string[]|null`，仅由第 4 节规则生成，v1 为 `QUANTITY_SHORTFALL|REVIEW_SKIPPED|REVIEW_FAILED|DEGRADED` 的集合。各嵌套对象和字段遵守第 3～5 节，列表与详情不定义两套含义，不返回阶段正文。

筛选参数全部是精确值，组合使用 AND；每种枚举只接受一个值，不做自由文本搜索。`trace_id` 匹配 sdk_trace_id 或 phoenix_trace_id；其他 ID 按绑定 ID 匹配。未知枚举、未知查询参数、无效时间／cursor、`scope=account` 未传 owner、`scope=platform` 同时传 owner 均为 422。dependencies 默认 platform，传 owner 且未传 scope 时按 account；alerts 默认不限制 scope，owner 筛选匹配告警归属账号，允许与 run scope 组合。分页默认 limit=20，范围 1～100。

### 6.2 分页与时间口径

- runs、overview 的 cohort 按 `accepted_at∈[from,to)`；alerts 按本轮 `first_seen_at∈[from,to)`，不是最近更新时间。依赖接口是当前快照，不接受 from/to，过期观测显示 unknown。
- alerts 传 alert_id 且未传 from/to 时，精确定位整个保留期内该轮次，不使用默认 24 小时；传显式窗口则继续 AND 筛选。不存在或已过期返回空 items；不能把默认窗口之外的通知误报为已过期。
- runs 按 `(accepted_at DESC,run_id DESC)`；alerts 按 `(first_seen_at DESC,alert_id DESC)`；dependencies 按 `(dependency_id ASC,scope_id ASC)`。使用 keyset cursor，绑定原筛选和首屏 `as_of`；后续页复用首屏实际 window，不重新计算默认“最近 24 小时”。
- `as_of` 是首屏服务端时间，上界截断到该时刻；新受理 run、新告警轮次不插入翻页集合。cursor 15 分钟有效，过期或筛选不符为 422。运行状态和已有行数据仍可更新，期间按可变状态筛选的集合可能变化；不承诺跨页数据库历史快照。前端刷新从第一页开始并按 ID 去重。
- 不返回不可靠的 total；`has_more` 通过多读一条判断，最后一页 `next_cursor=null`。空结果为 items=[]、has_more=false，不代表采集覆盖完整；公共 data_state、collection 和 warnings 负责解释缺口。

### 6.3 概览与统计分母

`window={from,to,time_basis:"accepted_at"}`。`collection={started_at,coverage_state:complete|partial|unknown,observed_runs,partial_runs,excluded_legacy_records:int|null,unknown_status_runs}`；started_at 为本次 v1 采集启用时间，coverage_state 结合已记录采集故障判断，不能仅因有部分 run 就声称覆盖完整。无法量化缺失请求数时，excluded_legacy_records 为 null 并警告；未记录的失败不会被反推成 0。历史无采集批次全部排除，不补成功率。

以下为本窗口内“已观测 run”的统计，而非所有历史请求的完整成功率。所有比率仅纳入 collection_state 为 complete／partial 且该指标证据已知的 run，not_collected／unknown 记录排除，即便历史批次标签写着成功。每个比率统一返回 `{numerator:int|null,denominator:int|null,value:number|null,excluded_unknown:int|null,reason:null|no_samples|not_collected|incomplete}`；分母 0 时 value=null、reason=no_samples。采集故障造成无法确定全集时 reason=incomplete；已知样本的比率仍可展示，但必须附覆盖警告，不外推全平台。对未采集项使用 not_collected，不能制造 numerator=0。

| 指标与响应字段 | 分子／分母与排除项 |
| --- | --- |
| `execution.counts` | 六种执行状态的已观测数量；只有可查询完整观测集合时相应空桶才可为 0。未知执行状态单列 unknown |
| `execution.completion_rate` | completed／(completed+failed)；cancelled、accepted、running、unknown 不进入分母，另展示各自数量；标题注明“正常结束率”，不叫质量通过率 |
| `quality_metrics.shortfall_rate` | quantity_status=shortfall 的 completed run／quantity_status 已知的 completed run |
| `quality_metrics.review_skip_rate` | skipped_count>0 的 completed run／eligible_count>0 且 skipped_count 已知的 completed run；不要求审核、零成果及未知排除 |
| `quality_metrics.degraded_rate` | occurred=true 的 completed run／occurred 非 null 的 completed run；false 必须有完整采集证据 |
| `quality_metrics.attention_rate` | quality.status=attention 的 completed run／quality.status 已判定为 met 或 attention 的 completed run；同一 run 多原因只计一次，not_evaluated／unknown 排除 |
| `quality_metrics.review_coverage_rate` | 完整记录最终审核计数的 completed run 中 Σcovered／Σeligible；eligible=0 排除，未知计数 run 排除，并返回 excluded_unknown |
| `regeneration_metrics.run_rate` | attempt_count>0 的 completed run／attempt_count 已知的 completed run；另给 attempt_total、total_attempt_ms 和 sample_runs，任一总量缺采集时须标 partial，完全无采集为 null |

`current={as_of,accepted_count,running_count,suspected_count,active_alert_count}` 为该时刻保留记录的当前值，包含第 8 节延后清理的活动状态，**不受 overview 的历史 from/to 限制**，但沿用 owner／entrypoint；active_alert_count 只计当前筛选范围可归属的 firing 轮次，entrypoint 生效时排除无法归属入口的共享依赖告警。各字段不可测为 null。真实队列深度不在首期契约中；accepted_count 仅表示已受理未开始，不叫持久队列长度。

`retention={trace_days:3,summary_days:14,cleanup_interval_hours:24,last_cleanup_at:null或时间,last_cleanup_status:success|failed|unknown}` 返回实际配置值，3／14／24 为默认值而非固定字面量。清理失败和观测陈旧须在 warnings 中可见。

`self_monitoring` 拟返回运维链路自身的安全摘要：事件采集延迟、SQL 写入失败、事件丢弃、Phoenix 导出失败／积压、最近一次告警评估、最近一次清理、通知投递失败、运行／trace 关联缺失、存储空间和当前生效阈值。当前前端映射为第 1.2 节可选 `metrics` 结构，使用 `observed_at/fresh_until/unknown_reason/effective_config`。后端内部的最近成功／失败时间、来源及安全原因码如何投影到此结构仍待 G1 冻结，不能将旧设计字段 `checked_at/last_success_at/last_failure_at/threshold/source/reason_code` 当作当前前端已支持的同名指标字段。不可观测值按实际返回 null，状态为 unknown 或 monitoring_unavailable，不改变业务 execution／quality／trace 字段。

M9 的访问审计写入内部审计记录，不新增第六个 ops 查询接口。正文查看、Phoenix 跳转、运行／告警详情和通知读写均产生审计事件；审计失败时禁止放行受控正文，前端只收到安全错误状态。

| 403 | `FORBIDDEN` | 非管理员拒绝，文案沿用“需要管理员权限” |

## 7. 依赖、异常与站内通知

### 7.1 DependencyStatus

字段为 `dependency_id,kind,scope,scope_id,owner_user_id,status,credential_scope,source,checked_at,fresh_until,last_success_at,last_failure_at,consecutive_failures,consecutive_successes,error_code,affected_run_count,collection_state`。ID 为稳定逻辑标识，禁止使用连接串或密钥指纹。`scope=platform|account`，平台 scope_id 固定 `platform`、owner 为空；账号 scope_id 为对应账号 ID。`credential_scope=platform|personal|none|unknown`；`kind=model|embedding|reranker|redis|vector_store|database|phoenix`。

`status=healthy|degraded|unavailable|unknown`；`source=passive|probe|mixed|none`。实际调用结果是被动证据，受控无正文探测是 probe，不因查询后台而主动调用模型。样本默认有效 300 秒，fresh_until=checked_at+有效期；从未观察时所有时间、计数为 null，source=none。当前依赖解析器验证时间格式、scope 与非 unknown 状态所需时间非空，保留服务端原状态；尚不在解析边界拒绝 `fresh_until <= checked_at`。页面要求 `checked_at <= generated_at` 且 `fresh_until` 晚于当前估算时间，否则显示 unknown，不能把页面降级当作解析拒绝。自监控扩展另有 `fresh_until > observed_at` 的结构校验，两者边界分别记录。网络失败不叫鉴权失败；部分能力失败但仍有明确替代路径可标 degraded，无当前可用证据不得标 healthy。

模型默认观察 SDK Agent 已发生的调用；同一依赖与 scope 的连续样本按观测序号累计，乱序或重复样本不影响失败／恢复次数。`error_code` 为 `AUTH_INVALID|QUOTA_EXHAUSTED|TIMEOUT|CONNECTION_FAILED|SERVICE_ERROR|UNKNOWN` 等安全分类；affected_run_count 为当前 5 分钟内去重 run 数，证据不足为 null。

个人凭据鉴权、额度错误只形成 account 级状态／告警并关联该账号运行；不能累加成平台共享模型连续失败。平台故障必须有同一共享依赖的独立平台级证据，不能仅凭“多人失败”推断。Phoenix 健康只说明服务级观测结果，绝不改变任何单条 trace 的 availability。

### 7.2 AlertEpisode 与去重

每个告警轮次字段固定为：`alert_id,dedupe_key,episode_no,rule_id,severity,scope,scope_id,subject_id,owner_user_id,status,condition_state,first_seen_at,last_seen_at,last_evaluated_at,resolved_at,occurrence_count,affected_run_count,sample_run_ids,evidence,notification,last_transition_reason`。依赖规则继承对应 platform／account scope；运行规则为 run scope、scope_id=run_id 并记录归属账号；质量聚合默认 platform scope、scope_id=platform、subject_id=all。

- `status=firing|resolved`；`condition_state=active|clear|unknown` 单独表示最近评估。采集故障时维持 firing 且 condition_state=unknown，不宣布恢复。`severity=warning|critical`，rule_id 及默认级别见下表。
- `dedupe_key` 按 `(rule_id,scope,scope_id,subject_id)` 的规范化序列化值生成稳定键；subject_id 为逻辑依赖 ID、run_id 或聚合入口 `parameterized|conversation|all`。不包含正文、错误全文、时间戳、trace_id 或可变显示名，避免同类错误每次产生新键。
- 同一键最多一个 firing 轮次。首次触发创建 alert_id，episode_no 从 1 开始；持续命中只更新同轮。恢复后再次触发创建新的 alert_id，episode_no 加 1，保留上一轮 resolved；14 天清理后仅可回收已无保留轮次的序列，episode_no 不是永久全局序号。主键及通知唯一键使用 alert_id，避免回收后的碰撞。
- occurrence_count 统计去重异常证据数，不按轮询次数增加。运行规则以 `(run_id,rule_id)` 为一条；依赖按失败观测 ID；质量窗口按新进入窗口的异常 run ID。affected_run_count 为本轮关联的去重 run 数；无法获知为 null。sample_run_ids 最多 5 个，只是样本，不作为精确影响数量。
- last_seen_at 仅随新异常证据更新，last_evaluated_at 随评估更新；未知评估不得延长异常证据寿命。run_id 筛选查询本轮完整的去重运行关联，不只查最多 5 个 sample_run_ids；关联与轮次一同遵守摘要保留期。
- `evidence={metric,value,numerator,denominator,threshold,window_from,window_to,sample_count,reason_code,reason_counts}`，均为安全数值、时间及枚举，无适用数值为 null。quality_attention 的 reason_counts 按质量原因码记录窗口内去重运行数，同 run 可出现在多个原因桶，原因桶之和不作为异常总数；其他规则不适用时为 null。恢复原因使用 `RECOVERED|RUN_TERMINATED|HEARTBEAT_RESUMED|BELOW_THRESHOLD` 等，不能粘贴异常内容。

| rule_id／默认级别 | 触发条件与口径 | 恢复证据 |
| --- | --- | --- |
| `dependency_failure`／critical | 同一依赖及 scope 连续 3 次失败；账号凭据异常仍只在 account scope | 同 scope 连续 2 次成功；无新样本不能恢复 |
| `waiting_suspected`／warning | accepted 且未实际开始超过 30 秒，并持续观察命中 120 秒；即最早约受理后 150 秒触发，按 15 秒评估粒度，可配置 | 确认开始，或明确失败／取消；监测中断重置连续观察计时，不按墙钟补足 |
| `long_running_suspected`／warning | running 且 started_at 已知，实际运行超过 600 秒 | 有权威终态；不得通过修改超时阈值直接伪造业务结束 |
| `heartbeat_stale`／warning | running，最近 heartbeat 超过 90 秒；尚无首次心跳时从 started_at 计时 | 新鲜心跳，或权威终态；只改观察标记 |
| `run_failure`／critical | 一次权威 failed 事件；run scope，只通知一次 | 这是离散故障事件，建轮并保存通知后即 resolved，reason=RUN_TERMINATED；恢复不意味着本次业务成功，不发送“已成功”通知 |
| `quality_attention`／warning | 按 completed 的 finished_at 在最近 5 分钟内取样；分母为 quality.status 已判定 met 或 attention 的去重 run 数，分子为其中 attention 的去重 run 数，同 run 多原因只计一次；有效样本≥10 且 attention 比例≥20%，默认全平台 all 聚合 | 使用相同窗口、执行状态及质量判定口径，有效样本≥10 且 attention 比例<20% 连续 120 秒；低样本／缺采集为 unknown，不宣布恢复，连续计时重置 |

单次题量不足、跳审、审核未通过和降级始终保留 run 原因明细；默认仅以合并 quality_attention 发送质量聚合告警，不为各原因再分别设置 20% 触发门槛，避免各项不足 20% 而整体异常已达 20% 时漏警。概览保留各原因细分比率及 attention_rate。质量告警的 finished_at 窗口不同于概览 accepted_at cohort，evidence 明示窗口，前端不得拿两个数字直接相减。未知及历史未采集数据仍按 6.3 排除，不能因样本小隐藏详情异常。频繁重出没有已配置阈值时只展示 unconfigured，不创建相应告警。

### 7.3 站内通知

`notification={last_sent_at,last_kind,next_eligible_at}`，last_kind 为 `trigger|reminder|recovery|null`。触发首条通知发送给当前启用的管理员；持续 firing 至少间隔 600 秒，只有出现新异常证据才再发送 reminder，不按每次轮询发送。恢复可立即发送一条 recovery；恢复后新轮 trigger 不受上一轮冷却限制。离散 run_failure 只发 trigger，不发 recovery。

后台以 `(recipient_admin_id,alert_id,notification_kind,notification_sequence)` 保证通知写入幂等；通知意图与轮次变化一起持久化后异步投递／重试，避免刷新页面重复创建。恢复轮次关闭后停止发送其待发 reminder。收件人禁用后不再投递；不向普通账号发送管理员运维摘要。

沿用现有通知列表、未读数与已读机制。实施时扩展现有通知 schema／前端映射，新增安全关联字段 `ops_alert_id`、`ops_episode_no`，kind 使用 `ops_alert_trigger|ops_alert_reminder|ops_alert_recovery`；title/body 只放固定安全摘要，不放正文。告警页面跳转通过 ops_alert_id 定位保留的轮次；轮次已清理显示“记录已过保留期”，不要求新增第六个接口。通知已读不等于告警已恢复；首期不新增确认、屏蔽或处理操作。

### 7.4 运维系统自监控、容量与访问审计

M9 的健康摘要和自监控告警使用与业务告警相同的安全字段边界，但必须区分“业务依赖异常”和“监控链路异常”。最小观测项包括：事件采集延迟、SQL 写入失败、事件重复／乱序／丢弃、Phoenix 导出失败与队列积压、告警评估最后成功时间、清理最后成功时间、通知写入／投递失败、运行与 trace 关联缺失、SQL／Phoenix 存储空间及配置陈旧度。

自监控状态至少使用 `healthy|degraded|unavailable|unknown|monitoring_unavailable`。后端须保留观测、最近成功／失败、有效期、安全原因和来源证据；这些内部字段与第 1.2 节前端 `observed_at/fresh_until/unknown_reason/effective_config` 的映射待 G1 冻结。监测器停止、观测过期或自监控存储不可读时不得返回健康或“无异常”；自监控异常不改写任何业务运行终态。

容量指标按配置的 `warning|critical` 两级判断，首期只读展示实际生效阈值。至少对事件处理延迟、Phoenix 导出积压、事件丢弃数、通知投递积压和存储空间提供当前值、阈值、窗口、样本和状态。缓冲满时优先保留运行终态、质量摘要和根 trace 关联；子 span、详细正文允许有界丢弃，丢弃、脱敏失败和重试耗尽必须可计数。通知失败执行有界重试，失败本身形成自监控异常，不由页面刷新驱动。

访问审计事件至少包含 `audit_id,actor_admin_id,occurred_at,action,target_type,target_id,result,reason_code`；`action` 覆盖运行详情、告警详情、Phoenix trace 跳转、对话／模型调用正文查看及通知读写。审计事件不包含正文、凭据、Cookie、认证头或原始异常。正文默认隐藏，单条 trace 需独立 Phoenix 授权和审计写入成功；权限拒绝、审计失败、过期和查询故障分别表达，不能返回可用正文链接。审计记录的保留期不超过其安全需要，具体配置在 G1 冻结。

当前前端异常详情使用第 1.2 节可选 `guidance={impact,owner_module,manual_action_required,next_step}` 与独立 `effective_config`，并提供已知规则的固定安全指引和未知规则通用指引；静态指引不是实际处理记录。早期拟议的顶层 `impact_scope/runbook_ref` 尚未映射，若保留须在 G1 明确转换；任何未来运行手册引用只能定位本地固定章节，不能拼接用户输入。阈值来源只允许配置文件或环境变量，后台无在线修改接口；如未来需要动态调参，必须另行设计配置版本、权限和审计。正文真实访问及审计能力待完成，当前真实适配固定 not_integrated，不增加审计 API。

## 8. 保留、清理与失效边界

- 默认配置为 `ops_trace_retention_days=3`、`ops_summary_retention_days=14`、`ops_cleanup_interval_hours=24`，均允许在实施配置中调整；不是首期新增后台写接口。部署本地 Phoenix 时将详细追踪清理策略应用到实际项目，并验证清理任务确实执行。
- 详细追踪以 SDK 根 trace 创建时间起算 3 天；到 expires_at 后平台正文入口关闭，物理清理按每日任务执行，不承诺精确到秒或数据库文件立即缩小。不得只清平台映射而保留 Phoenix 正文；长运行跨过期限仍关闭已到期内容入口，后续迟到 span 也须受同一到期边界约束。
- run、阶段及数量历史摘要默认从 accepted_at 起保留 14 天，trace 映射与其同寿命；依赖历史从 checked_at 起算；告警轮次从 last_seen_at／resolved_at 的较晚者起算；通知关联摘要从通知 created_at 起算。已关闭历史按这些到期边界正常清理，当前依赖快照仍遵守新鲜度，保留记录不代表观测新鲜。
- 活动运行延后清理：accepted／running，以及已受理但无权威终态、仍需检测的 unknown run，不能仅因超过 14 天就删除或隐藏。保留其运行摘要与判定所需关联，详情仍可查；列表通过包含 accepted_at 的显式窗口查询，current 统计继续包含。不得伪造 finished_at 来满足清理条件；活动状态解除后按历史到期规则处理。
- 活动故障延后清理：对 firing 或因缺证据而仍待检测的故障，保留当前判定、去重、恢复及通知所需的最小状态，包括 dedupe_key、活动轮次、最近有效证据、连续计数／观察计时、关联标识及通知幂等状态。无新证据只使 condition_state=unknown，不能据此删除活动状态或宣布恢复；过期历史事件、已关闭轮次及非必要明细仍正常清理。
- 延后清理在内部清理记录中保存 entity_type、entity_id、hold_reason（ACTIVE_RUN／ACTIVE_FAULT／DETECTION_PENDING）、held_at、last_reviewed_at，并由每日清理复核；保护解除后恢复历史清理规则。保护只针对必要摘要，不延长 Phoenix 正文 3 天保留期，也不要求保留全部故障历史。
- 正文 3 天后、摘要仍在时：执行／质量／计数照常可查，trace 显示 expired。摘要默认 14 天到期且不满足活动保护条件时，逻辑过期后不再返回，即使等待物理清理；详情返回统一 404，不保留无限期历史正文索引或墓碑。
- 清理失败保留安全失败码、last_cleanup_at/status 并在 overview 警告，不把失败当已删除；清理恢复后可幂等补清。未采集 trace、到期、无权限、查询故障和未知分别展示，不能合并为业务失败。

### 9.1 G0 追踪验收

追踪接入模块通过参数化／对话业务入口驱动 SDK Runner，以合成对话、假模型、假工具和本地受控导出服务验证下列条件，并核对后续运行记录与界面的关联约定。此阶段尚不实施运维后端接口或为旧链路补临时采集；本轮前端仅按第 1 节授权例外先行，不改变以下真实验收要求。

1. 成功、模型失败、工具失败、审核跳过与检索／模型降级均有正确 SDK trace 和阶段证据；错误被捕获转为可交付结果时仍保留降级事实，不只看 HTTP 200。
2. 两账号并发、同会话两次运行、并行工具／线程及重出任务均归属正确；run 一次一个根 trace，内部尝试不串会话，不借用另一个账号正文。
3. 用明确的假敏感标记验证嵌套 JSON、URL、工具参数、异常及缓冲均已脱敏；认证接口及个人模型设置不采正文，不读取真实配置进行验收。
4. 导出断连、超时、队列满、重试耗尽与恢复不阻断业务结果；出题响应不等待 Phoenix flush，trace 缺失和业务失败分别记录。
5. 本地捕获出口请求，证明只有本地 Phoenix 目标、默认云端处理器已替换；在真实本地 Phoenix 中以合成样本按映射 ID 查询根和子 spans，不能仅靠假 exporter ACK 或 Phoenix 在线通过持久可读验收。
6. 用验收专用内存收集器核对第 3.3 节必要事件、业务提交边界与 trace 映射；无需先实现运维 SQL 台账或完整质量聚合。实际业务链路仍正常保存业务数据，不能把“不要求运维 SQL”解释为跳过成果事务。
7. 锁定 SDK／适配器／Phoenix 兼容版本并记录资源占用、缓冲／重试／关闭行为及限制。核对实际项目 3 天正文保留与每日清理配置；在隔离合成项目用缩短 TTL 或所选版本支持的过期样本方式，验证真实删除及未到期对照。无需等待真实 3 天，但必须说明这是加速验证，不声称已观察完整 3 天周期。所选版本无法满足约定保留策略时阻塞 G0，不以临时应用调度器替代能力验证。

G0 的完成边界仅为实际两类 SDK 路径、本地可查追踪、必要事件关联、脱敏访问、有界导出故障恢复以及 Phoenix 保留能力。运维 SQL 台账、持久事件幂等、独立周期心跳与重启恢复由 M2 实现；完整持久化质量统计由 M3 实现；定时探测、告警及通知由 M4／M5 实现；五接口由 M6 实现；SQL 14 天清理、活动保护、应用调度与作业记录由 M8 实现，均不是 G0 前置要求。长运行根 trace 到期、迟到 spans 和平台到期链接关闭需在 M8／G3 完成，不能用 G0 的加速删除样例宣称全部通过。未通过 G0 时继续修复接入；前端例外不作为通过证据。

### 9.4 G3 联合验收

联合验收最小矩阵：

| 合成场景 | 期望结果 |
| --- | --- |
| 历史成功批次但无 v1 采集、从未采集审核或重出 | 不冒充 run、不进入相关比率分母；显示排除／unknown，完全无样本的比率为 null |
| 正常完成、数量不足、审核 unknown 放行、重出成功后被去重丢弃 | 执行与质量分列，最终交付数及审核覆盖准确，attempt_count 不替换为保留数 |
| 修补沿用题目 ID 但内容改变；题干审核后答案／解析再次更新 | 产生新版本，旧结论保留但不冒充新版本全范围审核；缺证据为 unknown，不自动补审或记明确跳审 |
| 只完成题干难度审核，所需答案审核缺失 | 展示实际范围，最终要求范围覆盖不完整，不能判全面审核通过或质量 met |
| 题目事务已提交，随后助手回复关联事务失败 | 保留批次与准确最终集合，回复关联单独失败；不清零实际题量，也不因批次存在宣称整次正常结束 |
| 执行超 10 分钟、90 秒无心跳、受理等待持续命中 | 只加疑似标记和告警；迟到终态或心跳恢复正确解除相应条件，不改写业务历史 |
| exporter submitted、Phoenix healthy、具体 trace 查询无映射／未找到／部分可查 | 分别显示 unknown／pending 或 not_found／available+complete=false，不能一律显示可用 |
| 个人假凭据失败与共享 Redis 连续失败 | 前者只影响账号；后者 3 次失败告警、2 次成功恢复，过期无证据为 unknown |
| 同类事件重复投递、持续轮询、恢复后再次失败 | 同轮去重，10 分钟冷却，新证据才提醒；恢复一次，新轮独立 alert_id 和递增 episode_no |
| 5 分钟内 10 个 completed 且质量已判定的样本，1 个不足、另 1 个降级；单 run 另可命中多原因 | quality_attention=2/10 触发，原因桶分别展示；同 run 多原因只计一次，历史／未知不充当分母；不足 10 个样本不发聚合提醒 |
| 同口径足样本且 attention<20% 持续 120 秒，中途出现低样本或未知 | 连续足样本满足时恢复；中断时保持待检测并重置恢复计时，不误报恢复 |
| 正文到期、摘要仍在；已关闭摘要到期；活动运行／待检测故障超过 14 天 | trace 显示 expired；已关闭历史正常清理；活动运行摘要及故障最小状态仍保留可判定，并记录延后清理原因 |
| Phoenix 权限拒绝；主摘要存储失败；老通知通过 ops_alert_id 跳转 | 详情 200+forbidden；主摘要 503；alerts 仅传 alert_id 可定位默认 24 小时窗口外的保留轮次，不新增接口 |
| 翻页期间新 run、状态变化、cursor 过期、非管理员访问 | 新 run 不插入原 as_of 集合，状态筛选按约定可能变化；无效 cursor 422；非管理员 403 |

以上为待实施的 G3 验收标准，不表示已经执行或通过。
