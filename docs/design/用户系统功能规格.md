# 用户系统功能规格与认证设计

2026-11-12 邮箱绑定契约调整：三角色均可凭有效登录态及新邮箱 `email_bind` 验证码，为无已验证邮箱的账号完成绑定，包括历史未验证邮箱。绑定请求仅含 `email`、`challenge_id`、`code`，不接受 `current_password`；已验证邮箱仍须双码换绑，解绑仍验证当前密码，成功仍撤销全部会话。

## 当前 main 的目标与使用范围

账号由管理员开通，首个管理员由运维交互创建；教师、学生和管理员均使用固定 account 和密码。登录页默认密码登录，另提供邮箱验证码登录，不选择身份，由服务端识别 admin/teacher/student。邮箱是可选安全配置，三类账号均能在自己的安全区域绑定、换绑或解绑；学工号保留为资料。实现入口为 [认证路由](../../backend/app/api/auth.py)、[用户契约](../../backend/app/schemas/user.py)、[登录页](../../frontend/src/components/auth/LoginPage.tsx) 和 [会话模块](../../frontend/src/api/session.ts)。接口细节见 [用户系统实施规格](用户系统实施规格.md)，管理员流程见 [管理员与账号开通设计](管理员与账号开通设计.md)，跨模块边界和迁移见 [账号系统整合与审查修复](../implementation/账号系统整合与审查修复.md)。

## 本机 Turnstile 开关规则

用户无法登录时的临时关闭范围仅为 Turnstile 人机验证；账号密码、JWT/SQL 会话、CSRF、邮箱验证码及角色与资源权限继续生效。`TURNSTILE_ENABLED` 默认 `true`，显式 `false` 仅允许 `APP_ENV=development/test` 启动，且仅请求实际 ASGI peer 为回环 IP（如 `127.0.0.1` 或 `::1`）时跳过。非本机 peer 仍需完整 Turnstile；Host、Origin 或转发头不能替代实际 peer。production 配置 `false` 在启动配置校验阶段拒绝。

GET `/api/auth/config` 的 `AuthConfig` 增加必填 boolean `turnstile_enabled`，按当前请求返回有效状态。有效禁用时后端不调用 Cloudflare，前端不加载脚本、不因缺票据或 site_key 阻止登录及发码提交。`POST /api/auth/email-code` 和 `POST /api/auth/login/account` 的 `turnstile_token` 可缺省或为空字符串；有效启用时仍拒绝空票据并执行完整验证。关闭不替代密码或邮箱验证码，也不解决 SMTP 不可用。

开关修改须重启并刷新前端配置，不支持热更新；实际本机临时进程、后续持久化开关与验证记录见[账号系统整合与审查修复](../implementation/账号系统整合与审查修复.md)。

| 账号开通 | 管理员创建账号及初始模型设置；公开注册页面、POST /api/auth/register 与发码 purpose=register 删除，邮箱登录或发码均不创建账号 |

| 邮箱码登录 | POST /api/auth/login/email 仅 email、challenge_id、code，移除 role；仅已验证邮箱可登录，服务端识别三类角色。POST /api/auth/login/password 学工号登录删除，学工号资料和维护接口保留 |
| 登录页面 | 仅“密码登录”“邮箱登录”两种登录入口，默认密码模式；移除注册及身份选择，保留密码恢复和 admin_contact 联系指引。config.methods 固定顺序 account_password、email_code；开发填充返回并填写 account |
| 管理员开通 | 首个管理员由 create_admin.py 显式交互创建，无默认密码或密码命令行参数；已有管理员可创建三角色账号、搜索筛选、编辑显示名、重置密码、禁用/恢复，保护最后一个启用管理员；无角色变更或永久删除 |
| 发码与 SMTP | login/reset_password 在有效启用时经 Turnstile、始终经限流后统一 202、后台投递；不适用邮箱或投递失败均无有效码。email_bind 发码需 Bearer，绑定 user_id、auth_version、原邮箱快照和目标邮箱；旧、新邮箱换绑发码沿用匹配 change_id。认证邮箱发码同步失败 503，失败不重置限额 |
| 人机验证 | TURNSTILE_ENABLED 默认 true；false 仅 development/test 可启动且实际 ASGI peer 为回环 IP 时跳过。AuthConfig.turnstile_enabled 按当前请求生效；非本机仍完整验证，production false 拒绝启动 |
| 邮箱绑定 | 仅无已验证邮箱可用，包括无邮箱及历史未验证邮箱；有效登录态＋新邮箱专用 email_bind 验证码提交 PUT /api/users/me/email-binding，不再要求 current_password，验证邮箱占用、版本和原邮箱快照，成功写入已验证邮箱 |
| 邮箱换绑与解绑 | 已验证邮箱沿用旧、新邮箱双码换绑；DELETE /api/users/me/email 以 current_password 解绑，清空 email、email_normalized、email_verified_at，email_verified=false。三类账号均可操作，管理员在管理面板自己的安全区域配置 |
| 密码与邮箱安全 | 新密码 8–64 字符且 UTF-8 ≤72 字节；改密需旧密码，恢复需已验证绑定邮箱。绑定、换绑、解绑均返回 204，同事务变更认证版本并撤销全部会话，回默认密码登录页；不自动创建新会话。改密、恢复及管理员重置/禁用也撤销全部旧会话 |
| 学工号 | 仅为可维护资料，不参与登录；去首尾空白、保留前导零、区分大小写、全平台唯一。专用接口增改删均验证当前密码与认证版本，null 移除；不改变用户 ID 和资源归属 |

## 当前限制与验收边界

公开 login/reset_password 验证码须绑定用途、规范化邮箱、用户 ID 和认证版本，发码、邮箱登录验码、密码重置验码三处一致。安全复核已发现仅 purpose/email/version 无法隔离同版本邮箱跨用户转移，补用户 ID 绑定的修复已通过相关回归；邮箱解绑转给他人后，旧 login/reset 码不得作用新账号。部署后旧未消费挑战失效、需重发，无数据库迁移。该项纳入最终验收。

UserPayload 必含布尔字段 email_verified；界面按验证状态而非邮箱字符串是否为空选择绑定或换绑。历史邮箱不自动标成可信，未验证邮箱不开放邮箱码登录与恢复，但可用原 account/密码登录后取得有效登录态，再用新邮箱 email_bind 验证码完成绑定；已验证邮箱走双码换绑，或以当前密码明确解绑后再绑定。

绑定、换绑、解绑的验证码或密码错误、邮箱占用、过期、重放、跨用户 proof、版本或邮箱快照变化均不得改写邮箱。并发操作须在提交时重新检查版本、唯一性和 proof 消费；已验证邮箱不得提交 email_bind 代替双码换绑。安全变更撤销全部会话并按目标用户清 Cookie，跨标签不得清除其他账号状态。

本轮不新增模型字段或 Alembic 迁移，保留历史 account、密码哈希、users.id 和资源归属。邮箱缺失、未验证仅是只读审计的信息项，不阻断发布或密码登录；标识冲突、结构异常、角色/身份不一致及开发种子来源等独立门禁仍需处理。

验收需覆盖三角色的两种登录、无身份选择与注册入口、旧路由及 register 用途删除、学工号仍可维护、无邮箱和未验证邮箱密码登录、三角色自助邮箱配置、绑定限制与双码换绑、解绑后默认密码登录、全会话撤销及资源归属不变。具体契约与待执行检查见实施规格。

公开邮件投递使用进程内响应后任务，没有持久化队列；202 仅表示受理，进程中断可能丢失投递，冷却后重发。会话协调依赖浏览器 Web Locks；退出撤销失败仅在当前页面内存保留重试凭据，并持久化自动恢复阻断意图，页面重载不会自动确认服务端撤销。默认凭据的存在不等于服务连通。
