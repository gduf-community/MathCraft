## 本机登录临时调整（2026-11-09，已实现并在本机启用）

用户无法登录时的临时关闭范围仅为 Turnstile 人机验证；账号密码、JWT/SQL 会话、CSRF、邮箱验证码及角色与资源权限继续生效。`TURNSTILE_ENABLED` 默认 `true`，显式 `false` 仅允许 `APP_ENV=development/test` 启动，且仅请求实际 ASGI peer 为回环 IP（如 `127.0.0.1` 或 `::1`）时跳过。非本机 peer 仍需完整 Turnstile；Host、Origin 或转发头不能替代实际 peer。production 配置 `false` 在启动配置校验阶段拒绝。

GET `/api/auth/config` 的 `AuthConfig` 增加必填 boolean `turnstile_enabled`，按当前请求返回有效状态。有效禁用时后端不调用 Cloudflare，前端不加载脚本、不因缺票据或 site_key 阻止登录及发码提交。`POST /api/auth/email-code` 和 `POST /api/auth/login/account` 的 `turnstile_token` 可缺省或为空字符串；有效启用时仍拒绝空票据并执行完整验证。关闭不替代密码或邮箱验证码，也不解决 SMTP 不可用。

本次已向本机后台启动进程注入 `TURNSTILE_ENABLED=false` 并重启后端，不修改真实 `.env`、`local_secrets.py` 或密钥。恢复时以 `TURNSTILE_ENABLED=true` 重启后端并重新加载前端；若移除临时覆盖，须确认其余受控配置为默认 `true`。开关不热更新。

本机后端已通过启动进程环境 `APP_ENV=development`、`TURNSTILE_ENABLED=false` 重启，监听 127.0.0.1 并使用 `--no-proxy-headers`。8000 和 5173 返回 turnstile_enabled=false、available=true。新增 7 项后端针对性测试通过；前端 typecheck、lint（0 错误、15 条既有警告）、定向 ESLint、auth-session-regression、logout-session-regression 与完整 e2e-auth 均通过。真实 5173 的匿名浏览器检查确认零 Cloudflare 请求、登录按钮可用且无认证配置错误，未提交真实登录。OpenAPI/API 文档已重新生成并核对。2026-11-10 后端全量结果为 291 passed、79 subtests passed、21 failed：20 项对应本环境此前出现的 Chroma 数据库打开失败，另 1 项迁移建表子进程 30 秒超时；该迁移用例单独复跑 1 passed（7.51 秒），未修改代码，超时未再复现。Ruff 保留 10 项、Pyright 保留 19 项既有诊断，本次文件无新增。 其余原有数量保留为调整前记录。

## 当前限制与验收边界

公开 login/reset_password 验证码须绑定用途、规范化邮箱、用户 ID 和认证版本，发码、邮箱登录验码、密码重置验码三处一致。安全复核已发现仅 purpose/email/version 无法隔离同版本邮箱跨用户转移，补用户 ID 绑定的修复已通过相关回归；邮箱解绑转给他人后，旧 login/reset 码不得作用新账号。部署后旧未消费挑战失效、需重发，无数据库迁移。该项纳入最终验收。

UserPayload 必含布尔字段 email_verified；界面按验证状态而非邮箱字符串是否为空选择绑定或换绑。历史邮箱不自动标成可信，未验证邮箱不开放邮箱码登录与恢复，但可用原 account/密码登录后验证新邮箱完成绑定；已验证邮箱走双码换绑，或以当前密码明确解绑后再绑定。

绑定、换绑、解绑的验证码或密码错误、邮箱占用、过期、重放、跨用户 proof、版本或邮箱快照变化均不得改写邮箱。并发操作须在提交时重新检查版本、唯一性和 proof 消费；已验证邮箱不得提交 email_bind 代替双码换绑。安全变更撤销全部会话并按目标用户清 Cookie，跨标签不得清除其他账号状态。

本轮不新增模型字段或 Alembic 迁移，保留历史 account、密码哈希、users.id 和资源归属。邮箱缺失、未验证仅是只读审计的信息项，不阻断发布或密码登录；标识冲突、结构异常、角色/身份不一致及开发种子来源等独立门禁仍需处理。

验收需覆盖三角色的两种登录、无身份选择与注册入口、旧路由及 register 用途删除、学工号仍可维护、无邮箱和未验证邮箱密码登录、三角色自助邮箱配置、绑定限制与双码换绑、解绑后默认密码登录、全会话撤销及资源归属不变。具体契约与待执行检查见实施规格。

公开邮件投递使用进程内响应后任务，没有持久化队列；202 仅表示受理，进程中断可能丢失投递，冷却后重发。会话协调依赖浏览器 Web Locks；退出撤销失败仅在当前页面内存保留重试凭据，并持久化自动恢复阻断意图，页面重载不会自动确认服务端撤销。默认凭据的存在不等于服务连通。

## 历史记录｜2. 2026-11-04 实施前仓库基线与差距

下列 Redis token、localStorage、无注册及普通资料直改邮箱均是实施前状态；当前实现已经替换，见本文当前规则及实施规格。

- 当前应用入口 `backend/app/main.py`；用户模型 `backend/app/models/user.py`，账号、邮箱、手机、学工号各列独立唯一，邮箱目前可空。

## 历史记录｜3. 页面与主流程

### 历史记录｜3.1 登录页

本节是原分支的两种登录方案；当前另有“开通账号登录”，并保留教师/学生身份选择用于邮箱码和学工号登录。

保留教师/学生身份入口；认证方式分为“邮箱验证码”“学工号密码”，不额外开放传统用户名或手机密码登录。服务端根据账号实际角色校验所选身份，前端角色不能授予权限。

邮箱登录：填写邮箱 → Turnstile → 发码 → 填验证码 → 登录成功进入工作台。不存在的邮箱发码阶段返回统一受理信息，不发真实邮件；验证码提交时不建号，以通用失败提示提供注册入口，避免增加直接的账号枚举接口。

学工号登录：填写学工号、密码 → Turnstile → 服务端校验 → 建立会话。失败保留输入，仅重置已消费或过期的人机验证 token；密码只保存在组件内存。

### 历史记录｜3.2 注册页

邮箱、验证码、显示名称、教师/学生身份、密码及确认密码必填；学工号选填。先做人机验证和发送注册专用验证码，最后一次提交完成字段校验与邮箱验证。原稿曾仅要求前端确认密码；此点已由实现替代：后端同时接收 password 与 confirm_password，独立校验密码策略及两次一致性。

账号和个人模型设置在同一数据库事务创建；邮箱验证与学工号唯一冲突返回可处理错误，不能留下半个用户。注册成功返回访问令牌、用户信息并设置刷新 Cookie，直接进入工作台。

并发注册通过唯一索引兜底，不依赖“先查询不存在”；注册已提交但刷新会话生成失败时，明确返回“账号已创建，请登录”，不假报注册回滚，不自动重试创建账号。

### 历史记录｜3.3 忘记密码

填写邮箱 → Turnstile → 发送 reset_password 验证码 → 提交验证码、新密码、确认密码 → 更新密码并撤销全部会话 → 返回登录页。

验证码错误、过期、网络错误均保留新密码及确认密码；成功、用户离开表单或主动清空时销毁内存值。禁用账号不能借重置恢复 active。未注册邮箱不创建用户。

### 历史记录｜3.4 个人中心

- 普通资料：显示名、学校等沿用现有入口；禁止通用 PATCH/PUT 直接修改 email、user_no、role、密码或认证状态。
- 修改密码：登录态＋当前密码＋新密码；成功撤销所有会话，回登录页。
- 更换邮箱：已登录 → 建立绑定当前用户及当前邮箱的换绑事务 → 分别通过人机验证向旧、新邮箱发专用码 → 提交两个 proof 与新邮箱 → 原子换绑并撤销全部会话。
- 新邮箱必须未被其他账号占用；提交时再验唯一性与旧邮箱快照；不能拿注册码或另一换绑事务的码替代。
- 学工号：已登录＋当前密码；允许添加、更换、移除。唯一性提交时兜底；验证密码与更新之间校验凭据版本，避免并发改密后沿用旧验证。原有角色、主键和业务关联不变。
- 旧邮箱不可访问时无绕过验证入口，明确提示本期限制。

## 历史记录｜4. 认证与持久化设计建议

### 历史记录｜4.1 用户数据与登录标识

角色仅 teacher/student、account 不可输入的范围仅适用于原邮箱分支；当前 UserPayload 包含 admin，无邮箱账号使用 account 登录。

保留不可变 users.id 作为资源归属主键。保留历史 account 字段以兼容已有引用，新用户内部生成不可输入登录的 account，不用邮箱或学工号替代主键。

新用户增加 email_verified_at、auth_version。role 仅 teacher/student，identity 由 role 派生；新增约束前检查历史异常值。user_no 继续可空、唯一；移除写 NULL，不写空字符串。手机号可留作非认证资料，但退出登录标识范围。

邮箱去首尾空白、校验格式；域名小写并按明确规范存储。建议产品层把邮箱登录视为不区分大小写，迁移时先扫描大小写冲突，不静默合并用户；不移除加号标签或点号等提供商特性。学工号去首尾空白，保留前导零，禁止控制字符；初版保持大小写敏感，表单提示明确。

密码建议 8–64 字符，另校验 UTF-8 编码不超过 bcrypt 的 72 字节边界；禁止静默截断。继续校验已有 bcrypt 哈希，存储时不记录明文，不把 8 字符新策略作为旧账号登录拦截条件。验证码错误与密码错误都不输出请求秘密。

### 历史记录｜4.2 JWT 与立即撤销

建议访问 JWT 有效期 15 分钟，固定 HS256 算法、至少 32 随机字节签名密钥；部署可配置，不提供硬编码缺省密钥。仅使用成熟 JWT 库，不手写签名。固定校验签名算法、iss、aud、sub、exp、iat、令牌类型，以及可选 nbf；不能信任请求头指定其他算法。

claims 包含 sub、sid、auth_version、jti、iat、exp、iss、aud；不装载密码、邮件码、模型密钥或个人资料。权限从数据库用户与资源关系读取，不信任 JWT 内角色快照。

引入 auth_sessions 表保存 sid、user_id、创建时 auth_version、状态、创建/到期时间和刷新令牌摘要。每次受保护请求同时校验 JWT、用户 active、auth_version 和对应会话有效性。因此退出、改密与换绑立即影响尚未到期 JWT，而不是等待 15 分钟。

改密、重置、换绑在同一数据库事务更新数据、递增 auth_version 并撤销会话；不依赖提交后再清 Redis 才保证安全。后续按该方案修改禁用流程；auth_version 不因重新启用回退，旧会话不能复活。授权会话状态存储不可用时拒绝认证，不降级为只验 JWT。

并发边界：登录、发放新会话与刷新必须把校验得到的 auth_version 作为事务内条件再次核对，并与改密/换绑采用同一串行化或条件更新策略；不能在旧密码验证后读取新版本并据此签发有效会话。全设备撤销保证提交后新进入的认证检查拒绝旧凭据，不能撤回已经执行的业务操作；敏感写操作在提交事务中再次核对认证版本。具体数据库实现须以当前 SQLite 的并发行为验证，不假设其支持行级 FOR UPDATE。

刷新令牌使用高熵随机不透明值，而非第二个访问 JWT；服务端只存摘要。建议绝对最长 7 天，无无限滑动延期；每次刷新原子轮换，已消费旧值记录至到期，用于识别重放并撤销该会话族。普通登出只撤销 sid，全部撤销依赖用户版本。

同浏览器并发请求统一 single-flight 刷新，多标签通过浏览器锁或协调通道串行刷新；明确复用旧刷新令牌会撤销该会话，响应丢失时可能需要重新登录，不以无限重试或长期复用旧值掩盖风险。

### 历史记录｜4.3 浏览器存储与 CSRF

访问令牌仅存在内存；刷新令牌用 HttpOnly Cookie，生产 Secure、SameSite=Lax、Path=/api/auth，无 Domain。页面刷新调用 refresh 再取 me，不继续读取旧 localStorage token。

Cookie 认证的 refresh/logout 请求必须检查可信 Origin、JSON Content-Type 和 CSRF 防护头/令牌；绑定精确 CORS 来源，不能用带凭据的通配符。若未来跨站部署需单独评审 SameSite=None/CSRF，不偷偷放开。普通业务 API 仍使用 Bearer。

客户端对 token 过期最多刷新并重试原请求一次；仅在认证层确认未执行的请求允许重试，非幂等业务操作不盲目重放。初始恢复显示 loading，避免登录页闪现；刷新失败清内存与 Cookie 并回登录页。

## 历史记录｜5. 邮件验证码与 SMTP

当前公开 register/login/reset_password 发码均为响应后投递、统一 202；仅换绑发码同步失败返回 503。Redis 校验状态与 SQL AuthProof 唯一消费共同工作，不存在跨存储原子提交。

建议验证码为随机 6 位数字、5 分钟有效、最多错误 5 次；每邮箱每用途 60 秒内最多一次、每小时最多 5 次，每来源 IP 每小时最多 30 次。均为建议初值，可配置，按实际内部使用评估。

用途分别为 register、login、reset_password、email_change_old、email_change_new，严格绑定规范化邮箱；换绑另绑定 user_id、change_id、旧/新邮箱快照。发码返回不可预测 challenge_id；验码必须同时提交 challenge_id 和用途绑定，不能只按邮箱查码。

Redis 保存验证码的服务端 HMAC 摘要、到期、次数、状态；HMAC 密钥独立于 JWT 密钥。原子校验、扣减次数与消费，错误不立即删除，超过次数锁定。重新发送使旧 challenge 失效；并发发码原子控制频率，不能竞争出两份有效码。

跨 Redis/SQL 无分布式事务：以短期 proof/reservation 防并发消费，数据库事务内记录 proof 唯一消费或等效幂等凭证，成功后完成 Redis 消费；不得声称两个独立提交是原子操作。密码重置及换绑 proof 绑定 auth_version，事务提交前再次核对，防并发安全操作覆盖。

SMTP：生产 TLS/STARTTLS、认证与超时明确配置。密码不进入日志。发送失败不留下可提交的有效 challenge；限流失败计数不因邮件失败自动清零。可用性响应不泄露注册状态；服务商错误映射为脱敏业务错误。

换绑用途的发码必须有有效登录态，且服务端从 change_id 解析对应用户和邮箱，不接受客户端任意指定收件人。未注册邮箱的登录/重置发码使用不泄露存在性的统一响应，不发送有效登录/重置码，也不自动建号；登录页始终提供注册入口，最终失败使用通用提示。注册邮箱已占用的提示与限流需在实施时核对枚举风险。

验证码不放 URL、响应或日志。单元/集成测试注入内存假发件箱；开发假邮件模式只能显式开发环境使用，不能通过公开 API 泄露任意用户验证码。忘记密码与登录各用独立用途，验证码不可互换。

## 历史记录｜6. Turnstile 集成

前端嵌入官方组件，后端调用 Siteverify 验 token，检查 success、预期 hostname 和 action。发码 action 为 email_code，密码登录为 password_login；服务端按路由固定预期，不由客户端指定并信任。

Cloudflare 官方规定 token 五分钟有效且单次使用；失败、过期、重复、网络异常需重置组件取新 token。服务端请求有超时，安全重试复用同一个 Siteverify idempotency_key，不把已验证 token 用于多个业务操作。

注册、重置与换绑的发码请求都经过 Turnstile；验证码提交另有限流和次数校验，不强制每次输码再次挑战。人机验证不替代密码/邮件归属验证或权限校验。

- 开发：官方测试 Site Key/Secret 成对配置，可测试成功、失败和重复；自动化测试使用假 Siteverify，不访问 Cloudflare。
- 生产：缺真实密钥、域名白名单，或检测到官方测试密钥则启动校验失败/认证入口明确不可用，不静默绕过；外部异常按拒绝处理。
- 部署配置核心是网站 hostname；访问者 remoteip 是 Siteverify 可选参数，不是服务器 IP 注册门槛。只信任已配置反向代理提供的客户端地址，不直接相信任意 X-Forwarded-For。
- Widget Site Key 可公开，Secret 仅后端；不需要将网站接入 Cloudflare 代理或本期额外配置 Access/WAF 门控。

| PUT /api/users/me/user-no | Bearer、user_no 或 null、current_password | 更新后的用户，无身份变化 |
| GET /api/auth/development-account?role=teacher或student | 受控本机开发限制 | no-store，仅示例填充；生产路由不存在 |

统一错误 code：VALIDATION_ERROR、AUTH_FAILED、ROLE_MISMATCH、EMAIL_IN_USE、USER_NO_IN_USE、CODE_INVALID、CODE_EXPIRED、CODE_ATTEMPTS_EXCEEDED、RATE_LIMITED、TURNSTILE_FAILED、AUTH_SERVICE_UNAVAILABLE、EMAIL_SERVICE_UNAVAILABLE、TOKEN_EXPIRED、SESSION_REVOKED。冲突/限流及异常输出脱敏。限流返回 429＋Retry-After，依赖不可用 503；不返回堆栈、验证码或 token。

普通退出在 Cookie 缺失或已失效时仍清 Cookie；如有需撤销会话，通过有效刷新凭证/访问凭证绑定 sid，不能让请求传任意他人 sid。

## 历史记录｜9. 实现模块与兼容迁移

旧稿要求所有无邮箱旧账号发布前补齐；当前受控、启用且两个邮箱字段均为空的 account 账号允许走账号登录。历史未验证邮箱仍不能绕过验证，实际迁移审计见整合文档。

尽量保留当前边界：auth 路由只编排，认证会话、验证码邮件、人机验证拆成内聚服务；用户资料路由承接安全资料更新，使用既有模型/迁移目录。新增文件的准确清单在实现时同步 README，不提前创建空模块。

迁移顺序：

1. 检查现有 schema 与迁移版本；只用合成数据验证迁移。正式执行前操作者备份，日志仅输出数量/脱敏冲突。
2. 增加邮箱验证时间、认证版本、会话及 proof 消费数据结构，先允许历史邮箱为空；清理空串语义和唯一索引冲突，不静默改写或合并账号。
3. 既有邮箱不得自动标成已验证；在新登录流程开放前安排一次性、受控的历史账号绑定/验证步骤。若已有账号只有旧 account，没有邮箱或学工号，必须在发布前由数据拥有者按迁移清单补齐；不靠猜测邮箱或开放旧绕过入口解决。
4. 新认证入口切换时拒绝旧 mc_ token，清理浏览器旧 mathcraft-auth 存储。提示旧用户重新登录；不同时保留可绕过 Turnstile 的旧 /login 或公开账号＋旧密码改密路径。
5. 稳定 users.id，题库、个人配置、收藏、试卷等外键不重建。独立登录类型不再使用跨字段 OR 查询，解决标识歧义根因。
6. 通用资料更新禁止直接改绑定邮箱；保留现有非认证资料用途，前后端一起迁移。生产默认账号不可自动启用，部署前查开发数据残留并人工处理。

历史真实数据数量与状态本轮未读取。若发现旧用户无法按新规则登录或邮箱冲突，迁移列为阻断项，不在无确认情况下执行重置/清空。无需恢复 DeepTutor 单租户替身。

### 历史记录｜PR #8 修复后的契约边界（2026-11-05）

退出不再以浏览器共享 Cookie 选定会话：必须携带本标签签名有效的 Bearer，后端撤销其中 sid，仅同会话 Cookie 会被清除。注销独有地允许 access 已过期；业务认证仍拒绝到期令牌。Origin、JSON 与双提交 CSRF 校验保持，缺本地 access 时前端只清本地，不匿名注销其他账号。上传仅对显式 `ACCESS_TOKEN_EXPIRED` 重试一次，撤销、角色／账号切换和旧响应不能重放或回填。【当时边界，注册项已替代】当时登录／重置发码统一 202、注册／换绑失败 503；当前注册也统一 202，只有换绑发码同步失败 503。离线审计与 HTTP 共用 `app.auth_validators`，拒绝相同非法标识；响应模型及 422 脱敏结构、Cookie/CSRF/Bearer 输入完整进入 OpenAPI。

发码隐私补充：登录和密码重置先返回统一 202，再在响应后发送邮件；SMTP 成功、慢响应或超时均不改变已返回结构。只有成功投递的最新验证码可验证，进程中断可能丢失未完成投递，冷却后可重发。退出撤销失败时登录页提供“重试退出”，原凭证仅在当前页面内存中用于撤销，禁止刷新恢复。
