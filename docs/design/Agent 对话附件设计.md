# Agent 对话附件设计

状态为待实现，对应 GitHub Issue #29。方案以 MathCraft 的 `agent` 工作树为基线，参考本地 DeepTutor `a31d8262` 的附件生命周期。

## 目标与已确认需求

- Agent 对话页提供独立的附件入口。拖入 PDF、Word、Markdown 时，文件加入当前会话的输入草稿。题库文档继续由题库页面上传和管理。两处可共用底层格式解析器，选择、暂存和提取对话附件与题库选择无关。题库检索仍由会话原有的资料选择决定。
- 输入区支持拖拽文档、拖拽或粘贴图片。图片与文档可以混发，**单条消息合计最多 4 个原始文件**。待发送附件显示可移除的矩形文件名卡片。
- 浏览器在点击发送时把原文件和正文放进同一条对话请求。后端按 PDF、Word 和 Markdown 分别提取，随后把提取结果与正文交给同一轮 Agent 处理。
- 未发送附件跟随现有文字草稿按会话暂存。换题库或切换会话保留各自的输入，返回会话时恢复。新会话正式创建时迁移对应的草稿。
- 已发送附件的原文件和提取结果随用户消息保存。重新打开历史会话可看见文件名卡片并下载原文件。同一会话后续可按需引用文档的提取结果。删除会话时清理附件。

## 现状和改造入口

- 对话区拖拽将图片交给 `addChatImages`，其他文件只取第一份，并调用题库的 `uploadDocument`。替换对话入口的分流，所有受支持附件先加入草稿。当前创建会话仍要求已有题库和文档，本任务沿用该创建契约。见 [GenerateTab/index.tsx](../../frontend/src/components/tabs/GenerateTab/index.tsx)。
- 文字草稿已按会话在前端 `AppContext` 中暂存。将图片和文档加入同一个会话草稿生命周期，统一数量校验和删除入口。见 [AppContext.tsx](../../frontend/src/store/AppContext.tsx)。
- 对话发送支持 `request_id`、结果轮询、暂停和待确认恢复。附件需要参与这些路径，特别是现有续跑目前只携带待处理正文和图片。见 [chat.py](../../backend/app/api/chat.py)、[chat 模型](../../backend/app/models/chat.py) 与 [API schema](../../backend/app/schemas/api.py)。

## 发送和提取

1. 前端以浏览器 `File` 对象暂存。用户发送时冻结正文、附件顺序、模式与现有请求参数，切换会话时仍按发送时的会话写回状态。服务端确认解析成功且用户消息已保存后，移除本次发送的草稿快照，保留发送期间新输入的内容。
2. 复用 `POST /api/chat/sessions/{session_id}/messages`。建议在现有 JSON 请求之外支持 `multipart/form-data`，用一个 JSON 部分传递现有消息参数，用有序的 `files` 字段传递原始文件。纯文字和现有 JSON 图片调用保留兼容路径。新增上传路径以相同的 `request_id` 参与现有幂等、轮询和取消逻辑。
3. 后端先校验用户、会话归属、文件数量、字节数和格式，再将文件存到独立的对话附件目录。先逐个提取成功，再关联附件和用户消息，然后进入 Agent 编排。耗时解析使用现有执行设施处理，避免阻塞事件循环或持有长时间的 SQLite 写事务。分开记录用户消息已保存和出题执行已完成两个状态，出题结果及相关状态沿用现有提交边界。
4. 本轮上下文保留正文原样。按上传顺序将每份文档的片段连同附件 ID、文件名和可用页码作为独立资料传入 Agent。图片走现有多模态能力。附件正文只作为参考资料，用户文字仍用于识别出题意图与审批指令。每份文档都进入本轮资料清单，预算内尽量为每份文档保留预览。已保存的提取结果可由 Agent 按需读取。
5. 后端主动调用格式提取工具，解析过程对用户表现为一次发送。另提供一个供 Agent 读取同会话已保存文档片段的工具，按附件 ID 和范围读取，返回文件名、片段及可用定位信息。历史轮次按需使用，避免每轮反复拼入全部历史附件。当前会话之外的附件不可通过工具读取。

| 文件类型 | 首版提取方案 |
| --- | --- |
| PDF（`.pdf`） | 用现有 PDF 解析器按页提取文本并保留页码。没有文本层时使用已配置的可用 OCR，缺少 OCR 或无法读取时提供明确的文件级提示。 |
| Word（`.docx`） | 用现有 DOCX 解析器读取段落与表格文本。旧版 `.doc` 提示转换为 DOCX。 |
| Markdown（`.md`、`.markdown`） | 读取原始 Markdown 文本，保留标题、列表、代码块和公式标记。 |
| 图片（PNG、JPEG、WebP） | 保存原件并通过现有多模态通道传入本轮。与文档共用附件数量额度。 |

## 上传限制

| 限制项 | 首版要求 |
| --- | --- |
| 每条消息的附件数量 | 0–4 个。图片和文档一起计数。发送带附件的消息时至少有 1 个有效附件。 |
| 单个图片 | 1 字节至 5 MiB，含上限。 |
| 单个 PDF、Word 或 Markdown 文档 | 1 字节至 20 MiB，含上限。 |
| 每条消息的附件总大小 | 合计最多 25 MiB，含上限。 |

以原文件实际字节数计量。已有 JSON 图片入口按 Base64 解码后的大小校验。拒绝 0 字节文件，大小合规的文件仍需通过格式和内容校验。仅含空白的 Markdown 按无可用内容处理。没有附件时可发送有效正文。正文为空且没有有效附件时拒绝发送。

前端加附件时检查单件、数量和累计大小，并提示具体文件和超出的限制。后端以实际接收内容复核，在解析和永久保存前拒绝违规请求。请求整体超限或包含违规文件时保留输入和已有草稿附件。

## 内容提取预算

保存文本与模型输入分别设预算，建议提取文本单轮最多 150,000 字符，单件共享该额度，本轮自动注入文档片段总计建议不超过 12,000 字符，并计入实际模型上下文预算。超出提取额度时记录并展示截断状态。如果剩余额度无法为某个文档保留任何提取结果，返回该文件的超额提示。文档内嵌图、图表和公式的视觉输入暂列为后续范围，上传截图可使用当前图片通道。格式、提取预算、截断和 OCR 行为属于首版实施建议。

## SQLite、文件存储与读取契约

- 使用 Alembic 新增会话附件表，关联用户消息和所属会话。建议保存附件 ID、消息 ID、会话 ID、上传顺序、类别、显示文件名、MIME、字节数、相对存储位置、提取文本和截断信息。历史无附件消息仍能按原方式读取，并返回空附件数组。
- 原文件存到后端运行时数据目录下独立的对话附件路径，例如 `data/chat_attachments/<session_id>/<attachment_id>`。使用服务端生成的标识作为存储名。历史展示和下载使用原始显示文件名。SQLite 保存元数据及提取文本，不保存文件 Base64。
- 会话消息详情返回附件元数据和下载入口。建议新增 `GET /api/chat/sessions/{session_id}/attachments/{attachment_id}`，按现有会话归属规则授权，以下载响应返回原始字节。历史消息列表无需载入全文。Agent 的片段工具在服务端读取 SQLite 已保存的提取文本。
- 校验实际文件内容并将附件写入限定目录，拒绝超额、伪装格式和越界路径。用短事务关联用户消息和附件行。解析完成后，现有模式切换续跑、暂停和 Worker 恢复按附件 ID 复用原消息附件与已提取内容。模式切换续跑只读取原请求的附件。相同会话和请求 ID 的重放走现有在途检查和结果查询，验收只产生一轮消息和一套附件。
- 删除会话时一并删除 SQLite 附件记录，提交成功后清理磁盘附件目录。将仍在执行的请求标为取消并阻止晚到的上传或解析写入。未绑定的文件可回收，磁盘清理失败可重试。附件目录和数据库位于应用配置的运行时路径。

## 失败与重试

- 上传或解析失败发生在收录用户消息之前。建议整条请求暂不进入模型，响应标识具体失败文件，原草稿与全部待发送附件保留。用户可移除失败文件、重新选择或重试。清理本次未绑定的原件。
- 用户消息已收录后，模型失败归入当前请求状态。显式重试复用已保存的原文件和提取文本，并引用原用户消息。用原请求 ID 查询或重放仅返回该请求既有状态。客户端遇到超时先查询现有请求状态，确认用户消息是否已保存或仍在处理。
- 承接现有页面内存草稿机制。切换会话支持恢复，刷新和重新打开页面只从服务器恢复已发送内容。建议沿用附件可独立发送的交互，具体出题要求仍走当前模式的槽位校验。

## 验收标准

1. 未选题库时也能在对话区把三种文档加入草稿。按现有会话创建条件进入会话后，两张图片和两份文档可在同一消息提交，第五个文件会被拦截，且后端能独立校验。验证 0 字节拒绝、纯文字允许，以及 5 MiB 图片、20 MiB 文档、25 MiB 合计的等值和超限 1 字节边界。题库列表、题库文档和索引无新增记录。
2. 会话 A 的文字和附件在更换题库或切到会话 B 后仍属于 A。切回 A 恢复。删除某个待发送附件仅移除该文件。迟到的上传或读取结果不能写入 B。
3. 一次提交中可分别提取 PDF、DOCX、Markdown，并由假模型验证正文、正确的文档片段和图片进入同一轮。空文档、损坏文件、不可解析的扫描 PDF 和超额文件能给出对应反馈。
4. 重开会话后历史卡片包含正确的文件名。文件下载与原件字节一致。其他账号或其他会话无法下载、引用该附件。
5. 同会话后续提问可以按需读取旧文件片段。模式切换续跑、重复请求和模型失败重试都能保留正确的文档内容，同时不重复写消息或文件。
6. 删除会话后附件记录与原文件均被清理。验证删除和发送并发时可阻止晚到写回，删除事务回滚时原件仍可下载，写盘成功但入库失败的文件可回收。
7. 实现阶段同步根 `openapi.json` 与 `docs/api.md`，覆盖两种发送请求内容类型、历史附件元数据和下载接口。用临时 SQLite、隔离的测试 Redis 和假模型验证接口和数据归属，前端运行 `typecheck` 和 `lint`。

## DeepTutor 参考实现

DeepTutor 在模型调用前保存原文件，将提取结果与用户消息关联，历史附件通过受会话范围约束的来源清单按需读取。MathCraft 沿用本地会话草稿语义和现有请求协议，重试时显式复用保存的提取结果。

- 保存原文件、提取并写入用户消息。见 `deeptutor/services/session/turns/executor.py:312`。
- 历史附件以提取文本作为资料来源。见 `deeptutor/services/session/source_inventory.py:482`。
- 删除会话时清理附件目录。见 `deeptutor/api/routers/sessions.py:657`。
