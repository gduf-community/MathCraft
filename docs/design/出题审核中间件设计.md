# 出题审核中间件设计

本文说明 `backend/app/services/question_review.py` 的目标、使用范围、核心流程、数据契约、异常边界与验收标准。历史实现对应提交 `feat(generation): 出题中间件、盲评校准与模型超时修复`。

## 第一阶段交付设计

本节对应 [Agent 出题优化方案第一阶段](../requirements/Agent%20出题优化方案.md#一修复出题纠错和交付流程)。第一阶段的接口与异常处理按本节实施，后续各节记录历史实现。

### 共享编排与交付条件

同步参数化、后台参数化及对话出题共用同一编排。编排按请求的题型和目标档位维护配额，并在首轮及每轮补题沿用指定范围和来源模式。只有通过题面完整性、数学可解性、指定考点及解析方法范围、目标难度和成品一致性检查的题目才占用配额。

1. 依据完整题面独立求解，结构化区分正常作答、题设不足、待证命题为假、条件矛盾和无法验证。判断题判错并给出反例属于正常作答。要求证明为真的命题被反例推翻时，记录为题干缺陷。模型调用失败、输出无法解析或证据不足时，记录为无法验证并拦截。
2. 将反例、缺失条件或矛盾条件提供给修题步骤。每道候选最多定向修补一次，修订后从完整题面重新走验收链。修补后仍未通过则换题。原题模式下，若修订会改变原题的数学含义，优先换用另一道材料原题。解析方法超出指定范围时，优先在修补步骤中改写解析，再重新验收。
3. 联合核验最终题干、选项、答案与解析。选择题核对各选项的定义域、真假、正确项数量，并将成品答案标签映射回选项文本，再与独立求解结果比对。材料原题选择题在生成环节先按题号定位题块，依据片段内题号等标记、相邻入库切片或文档末尾确认边界，再核对题干及整组选项的标签、顺序和文本。材料和候选使用相同的公式定界符归一化规则。题块边界不明确、文本不匹配或存在多组冲突选项时，记录「原题选项缺失或无法与材料核对」并按原请求换题。证明题核对解析是否完成题目要求。难度不符的候选进入修补或换题。

相邻切片的题号与选项结尾相同（例如 `2.`）时，旧索引无法区分切片重叠和自然重复。此类边界按无法核对处理。
4. 首轮结束后，编排针对各题型和档位的实际缺额启动补题。全请求共用最多三轮补题预算，每轮仅补当时缺额，新增候选走同一验收链。配额达到或预算用尽时结束，交付所有通过验收并计入配额的题目。

### 结果契约

后台任务结果的 `review` 支持可选的 `groups`。每组对应一个请求中的题型和目标档位，包括交付为零的组。

| 字段 | 含义 |
| --- | --- |
| `type`、`difficulty` | 请求的题型与目标档位 |
| `requested`、`delivered`、`missing` | 原始请求数、实际交付数及两者之差 |
| `rejections` | 程序按实际拦截原因汇总被淘汰的候选题，以候选题为计数单位 |
| `generation_events` | 生成环节的事件汇总，用于说明生成失败或未产出候选等情况 |

同步 `POST /api/generate` 默认返回题目数组。传入查询参数 `include_review=true` 时，成功响应返回含 `questions` 和 `review` 的对象，采用同一分组汇总。对话在助手结果消息中展示按题型与目标档位汇总的请求数、交付数、缺额及主要拦截原因。足量、部分和零交付均能呈现，零交付时题目列表为空。

### 难度分与质量判定

难度按指定知识点范围内的最短合理解法评估。审题模型对步骤综合、概念抽象、计算复杂度、陷阱与非常规程度各给 1–5 分。后端按 20∶20∶15∶15 加权，除以权重和 70，结果保留两位小数。低、中、高、地狱分别对应 `[1, 2)`、`[2, 3)`、`[3, 4)`、`[4, 5]`。

知识点匹配与可解唯一属于质量审核。成品的题面、范围、选项、答案、解析均须通过检查，可解唯一评分不超过 2 时否决。候选题须同时通过质量审核并达到目标难度才可交付。题目沿用现有字段保存难度分和审核明细，历史题目的评分继续按生成时的结果保存。

### 第一阶段异常边界

- **首轮原题不足。** 原题模式按同题型各档请求数之和核对材料库存。确认不足时沿用入口的 `NEED_CONFIRM` 分支。对话保留题型和数量，清除来源模式槽位，请教师重新选择来源。排队任务和同步接口沿用各自的错误返回。
- **首轮个别组生成失败。** 可恢复的模型或输出异常记入本组的生成事件，其他组已有的候选继续验收。首轮没有可用候选的组仍可使用共享补题预算。
- **首轮所有组均因模型调用失败。** 若每组的所有出题批次均遇到模型调用错误，首轮按请求顺序返回第一组的脱敏错误。后台任务以失败结束，进度返回安全提示和空题目列表，`batch_id` 为 `null`。检索无结果、模型输出未形成可用候选或评审拒绝全部候选时，仍按共享预算处理并汇总各组结果。
- **补题失败。** 补题时遇到原题不足（包括 `NeedConfirmError`）、检索无结果或生成失败，将相关事件记入受影响组的 `generation_events`，保留已通过的候选及实际缺额。该轮计入共享预算，剩余轮次仍按原来源和范围尝试。补题失败走结果汇总流程，首轮的来源确认仅在首轮触发。
- **取消。** 初次生成、审核、修补、补题及写入前均检查取消。取消异常向调用方传播，停止后续调用和补题，沿用入口的取消处理。写入前确认取消时结束本轮，交付和入库均停止。已提交的批次沿用现有事务结果。

### 补全修订、计算验证与查重

独立求解通过后，补全结果按失败原因追踪。已确认答案和已核对选项作为定向解析修订的输入，整道题共用一次修订额度。新编选择题可以补齐未成形的干扰项。修订后继续走答案、选项、解析、难度验收与成品查重。补题按题型和目标档接收上一轮至多两项可操作的审核原因，并将原因转成固定命题提示。

联合验收、仲裁和修题调用的模型响应遇到 JSON、字段或解析公式格式错误时，使用原输入和格式反馈重试一次。新响应仍需通过该步骤的原有校验。格式重试独立于候选题的内容修订额度。第二次仍失败时沿用审核失败与补题流程。

对能完整解析的单变量计算题和精确数值题，先用 SymPy 确定结果，再核对答案、解析结论及选项。计算使用受限表达式和有限运行时间。无法解析、超时或超出覆盖范围时回退到独立解题与联合审核。

查重保留会改变数学含义的字符。历史收藏、试卷快照、同题库个人历史与预览成品按题型、题干和有序选项比较。成品使用向量召回相似题，再比较数学条件、所求和选项。向量服务或复核不可用时完成精确查重后继续交付。只有计入配额的成品进入本轮请求的后续查重语料。

### 第一阶段验收标准

复用无效多选、被反例推翻的证明题和越出指定范围的选项，检查拒绝项无法占用配额、证明题的反例进入修补或淘汰流程、修订后的成品重新验收。用多题型和多档位连续失败的批次检查全请求首轮后最多补三轮，以及足量、部分和零交付各组的题目、缺额、拦截原因与生成事件是否一致。分别覆盖首轮原题不足请求确认、补题原题不足保留已通过题，以及生成或审核被取消后的停止与写入边界。

## 历史实现

### 目标

命题模型一次给出的题目不能直接用。实测并发出题时十道题里有五题撞到同一考点，地狱难度题里约七成达不到目标档，答案与解析还会互相矛盾。中间件把查重、难度盲评、缺陷修补、独立解题收敛成一条固定流水线，题目通过后才写入题目预览。

另一个目标是修掉模型响应超时。生成阶段开启思考模式时，单题跑 3 分 19 秒仍无返回，十题并发会一起撞上 300 秒超时线。

### 使用范围

对话出题与参数化出题两条链路都经过中间件，入口分别是 `app/api/chat.py` 与 `app/services/generation.py`。知识点检索、HyDE、混合检索、题型编排仍在 `app/services/rag/`，不在本模块内重复实现。

### 核心流程

| 阶段 | 处理内容 | 并发方式 |
| --- | --- | --- |
| 考点规划 | 出题前让模型列出互不重复的细分考点，再按考点拆给单题批次 | 一次调用 |
| 生成 | 单题流式调用，关闭思考模式，单题预算 3000 token 加结构开销 400；完整对象即校验 | 六路 |
| 查重 | 与收藏、组卷记录、同题库历史题目做 bge-m3 语义比对，余弦 0.92 以上丢弃，批内同样互查 | 本地计算 |
| 盲评 | 不告知命题时标注的难度，独立解题后按六个维度打分，两次评分差超过 0.7 时第三人仲裁 | 每题两到三次调用 |
| 修补 | 按缺陷码做最小修补，只改必要字段，保持题型与考点不变 | 六路 |
| 换模板重出 | 修补未通过或数量不足时换难度模板重出，最多一轮 | 六路 |
| 补齐 | 仍不达标时按距离目标档中心最近的顺序补足数量 | 本地计算 |
| 解析 | 另起对话独立解题，覆盖命题阶段自带的答案与解析 | 六路 |

六维权重为知识点匹配 0.20、步骤综合 0.20、概念抽象 0.20、计算复杂度 0.15、陷阱非常规 0.15、可解唯一 0.10。加权总分 1 到 2 为低，2 到 3 为中，3 到 4 为高，4 到 5 为地狱，边界留 0.5 容差。可解唯一性过低、超纲、答案有问题时一票否决。加权总分由本地重算，不采信模型算术。

### 流式生成与结构校验

本节按 2026-11-13 合并代码同步，范围为 `rag/llm.py`、`rag/question_gen.py`、
`rag/prompts.py` 和 `schemas/question.py`；后文原有实测数据仍为历史批次。

1. 提示词提供字段结构与示例，要求输出 `<questions>{"questions": [...]}</questions>`，
   公式采用 `$...$` 或 `$$...$$`。标签是模型输出约定，不是新的 HTTP 消息格式。
2. `chat_stream()` 仅累积有效内容增量。滚动解析器找到 `questions` 数组后，
   每个完整对象立即交给 `Question.model_validate()`；字段校验失败中断当前批次解析。
3. 流结束后对剩余可恢复内容使用 `json-repair`，修复所得对象仍须通过相同校验。
   无有效题目或字段不合法时，最多附带一次错误摘要与输出片段重新请求，预算保持不变。
4. 返回前丢弃不匹配的题型，补充题目 ID、默认分值、目标难度及文档名称；
   仍无有效题目则抛出生成错误，由原有批次及审核流程处理。

Pydantic 使用现有 `Question` 的默认字段和兼容转换，并非提示词中“禁止增删字段”的
逐字强制实现，不能据提示词宣称所有缺省或额外字段均会拒绝。题干、选项、答案和解析
会去掉代码栅栏，将 `\(...\)`、`\[...\]` 统一为美元定界；这只处理格式，不验证数学正确性。
格式通过后仍须经过查重、盲评、修补与独立解题，不向浏览器提前交付未审核对象。

`json-repair` 同时用于审核低温 JSON 调用的解析兜底；它只修复结构，审核内容仍由
各阶段解析规则处理。审核初始预算失败后最多再用 1.4 倍预算调用一次。

### 接口与数据契约

新增两个 HTTP 入口，完整契约见根目录 `openapi.json` 与 `docs/api.md`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/chat/sessions/{session_id}/progress` | 前端每 1.5 秒轮询阶段百分比与文案 |
| POST | `/api/chat/sessions/{session_id}/cancel` | 暂停生成，后台在检查点停下且不落库 |

生成任务结果新增 `review` 字段，含 `duplicates`、`repaired`、`regenerated`、`solved` 四个计数。题目新增 `difficulty_score`、`blueprint`、`difficulty_review`，落库列对应 `difficulty_score`、`blueprint_json`、`review_json`，由两条 Alembic 迁移 `d9f4a2c7e815` 与 `e3b7c1d94a62` 引入。迁移链从 `c3e8a1f5b279` 起，升级前需确认该版本已存在。

### 异常边界

- 向量服务不可用时跳过查重，不阻断出题。
- 盲评、修补、解析任一环节的服务异常只降级并写日志，保留原题与原有答案，不让整批失败。
- 单批生成失败只丢该批，由补齐轮补上；一道都没出时才把真实异常抛给前端。
- 生成端 JSON 截断或结构异常按上述滚动解析与修复流程处理；字段校验失败或未解析出题目时最多反馈一次错误重试，不再使用旧的生成预算递增流程。流式传输异常不作为结构错误重试。审核 JSON 调用的修复与预算重试遵循本节上方说明。
- 接口不认关闭思考模式的参数时退回默认调用，保证 DeepSeek 官方实现可以直接使用。
- 对话与出题模型配置只保留 DeepSeek 官方地址与模型名，个人密钥通过现有用户模型设置接口保存，不写入仓库。

查重语料按题库和当前用户隔离。独立求解一次返回答案、解析与置信度，低置信度写入自检说明。

### 验收标准

流式增量验收应覆盖任意内容分片、标签／代码栅栏、截断 JSON 修复、字段错误反馈重试、
无有效题目、错误题型过滤和公式定界规范化；验证使用模型替身，不连接真实服务。
原有审核实测见[出题实施记录](../implementation/快速出题取消与清空.md)，不作为当前流解析增量的测试结果。

共享题库语料隔离与独立求解的变更及验证见[出题审核中间件实施记录](../implementation/出题审核中间件实施记录.md)。
