# 对话出题必填信息检查

状态：已实现（2026-10-30）。

## 目标与使用范围

保留 `/api/chat` 现有的多轮信息抽取、累积与追问流程。教师明确题型、每种题型数量、出题范围、题目来源和难度后，才启动生成。本次修复移除题量默认 5 道的行为；参数化 `/api/generate` 继续遵循其原有契约。

## 核心流程

1. 信息抽取只采用教师明确表达的要求，未提及的字段保持缺失；不得使用助手举例中的数字，也不得自行分配多题型的总题量。
2. 将新信息合入已有要求。教师没有重新说明数量时，保留之前明确的数量；新增题型未给数量时保持缺失，不补默认值。
3. 逐项检查题型、各题型数量、范围、来源和难度。缺少题型时一并询问题型与数量；题型已知时，只列出数量缺失的题型。空白范围也视为缺失。
4. 信息不完整时返回追问、累计状态、空题目列表及 `done=false`，不调用题目生成服务。没有追问轮数上限。
5. 全部信息齐备后构造生成参数；参数构造也拒绝不完整要求，避免绕过编排检查时回退默认数量。

## 数据契约与异常边界

请求与响应字段不变。`slot_state.types` 仍为题型与数量的列表；尚未确认的 `count` 为 `null`。`slot_state` 沿用前端逐轮回传方式。

数量沿用 `TypeCount` 的约束，每种题型为 1–20 道。布尔值、非整数、非有限数字、零、负数和超过上限的数量不能作为有效数量；在没有有效历史数量时继续追问。已有有效数量不会被后续未提及数量的抽取结果清空。

模型负责从教师自然语言中抽取信息，后端负责结构和完整性检查。历史会话中已经填入的 5 无法辨别是教师明确要求还是旧代码默认值；本次不追溯改写历史状态，需要重新确认的旧会话应重新开始。

## 验收标准

- 只给题型但未给数量时持续追问，不出题。
- 多题型中仅一部分明确数量时，只追问尚缺数量的题型。
- 后续补齐数量后，保留先前已明确的数量，齐备后才调用生成。
- 范围或难度缺失时，即使数量齐备也不生成。
- 非法数量不能启动生成，不能自动截断小数或默认补为 5。
- 回归测试使用假的抽取与生成服务，不连接真实模型或知识库。
