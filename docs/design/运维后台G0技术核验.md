# 运维后台 G0 技术核验

日期：2026-11-12。范围：甲在无需外部 SDK 业务交接时可独立完成的技术资料核验与隔离部署试接入。本文不是实际业务入口 G0 通过证明，不实施运维 SQL、正式周期心跳、质量统计、告警或五个 ops 接口。

本文区分研究代理核对的官方资料、主代理执行获得的本轮证据和仍需外部业务交接的部分。所有试验仅允许合成内容、假模型、假工具和隔离项目；真实凭据、用户正文及原 RAG 验收数据不参与试验。

## 2. SDK 原生追踪到本地 Phoenix

Arize 官方集成使用 `OpenAIAgentsInstrumentor` 接入 OpenAI Agents SDK，并通过 OpenTelemetry 导出至 Phoenix。HTTP OTLP 接收路径为 `/v1/traces`。官方示例中的真实 OpenAI 模型调用不属于本轮验收：本轮用假模型和假工具执行 SDK，不填写真实模型 API Key。来源：[Phoenix 的 OpenAI Agents SDK 集成](https://arize.com/docs/phoenix/integrations/llm-providers/openai/openai-agents-sdk-tracing)、[OpenInference 包示例](https://pypi.org/project/openinference-instrumentation-openai-agents/)。

本轮本地 HTTP 端点为 `http://127.0.0.1:6016`，追踪发送至其 `/v1/traces`。导出端和读取端都必须显式指定本地地址，不从既有个人配置或业务模型设置发现目标。

本轮主代理已核对所锁 instrumentation 的 `instrument(..., exclusive_processor=True)` 会替换 SDK 默认处理器。必须在首条 trace 前完成替换；只追加本地处理器不能作为默认云端处理器已移除的证据。应检查最终处理器链及实际出口，而不是只检查一个环境变量。

正文与属性在写入有界导出缓冲前脱敏，不能只在最后一次 HTTP 发送时处理。模型调用失败、工具失败和捕获异常后的降级应分别保留合成事实；根 trace 成功不证明质量达标。`run_id`、账号、会话和批次关联由 SDK 业务提供，跨线程和并行工具需要显式传播上下文。

本轮主代理报告已完成隔离合成追踪的实际写入与读取，共 5 条 trace、45 个 span；此数字应与本轮机器可读证据对应。它证明本地技术路径，不证明参数化／对话实际业务入口已调用 SDK。

## 3. 独立访问控制与自动化凭据

Phoenix 官方支持开启认证，并通过 `PHOENIX_SECRET` 签名；`PHOENIX_ADMIN_SECRET` 可以作为管理访问的 Bearer 凭据。后者须至少 32 字符、包含数字和小写字母、与前者不同，并且要求前者已配置。该方式允许隔离环境脚本完成管理 bootstrap，无需读取用户密码或复用 MathCraft 会话。来源：[Phoenix 认证配置](https://arize.com/docs/phoenix/self-hosting/features/authentication)。

需要 API key 时，官方 REST 源码提供 `POST /v1/system/api_keys`，请求包装为 `data`，字段包括 `name`、可选 `description` 和 `expires_at`；创建结果仅当次返回 key，列表不再返回。创建须由有权限的管理会话或 admin secret 发起，已有 API key 不能继续签发新 key。来源：[官方 API key 路由源码](https://github.com/Arize-ai/phoenix/blob/main/src/phoenix/server/api/routers/v1/api_keys.py)。此链接为官方当前源码，本轮实际使用时须以固定镜像暴露的 OpenAPI 为准，不将 main 源码当作已锁版本契约。

临时管理秘密和 API key 仅保存在本轮隔离、被忽略的本机配置中，不写入报告、普通日志、追踪或通知。本轮主代理已经实测无凭据／无效凭据被拒绝、有效凭据成功（401／401／200）。MathCraft 管理员身份不自动授予 Phoenix 权限。

镜像端口只绑定宿主机 `127.0.0.1`。容器的专用 bridge 与回环绑定分别核对；Docker 网络 `internal:true` 在本机 Docker 29 的测试中导致 host publish 不生效，不能把该配置存在当作可访问性证据。其他遥测设置只按固定镜像的真实配置能力核对，不编造“已关闭全部遥测”结论。

## 4. 保留与清理：本轮最终选择

**本轮选用唯一机制：应用通过公开 REST 时间窗删除接口执行清理。G0 仅在隔离合成项目手动验证一次；G0 后由乙在 M8 接管每日、3 天正文保留的调度。Phoenix 原生时间保留设为 `maxDays:0`，不再并行启动原生到期清理。**

主代理已从固定 Phoenix 21 镜像核对并实际采用：

```text
DELETE /v1/projects/{project_identifier}/traces
查询参数：start_time、end_time
```

实际请求参数格式、时间边界及返回行为以该固定实例 OpenAPI 和本轮删除前后读取结果为准。该接口是受支持的管理入口；禁止直接删除 Phoenix 私有表或文件。公开路由来源：[Phoenix 官方 traces 路由](https://github.com/Arize-ai/phoenix/blob/main/src/phoenix/server/api/routers/v1/traces.py)，明确按 trace 开始时间执行左闭右开窗口并级联删除 spans。此 main 链接作为资料来源，不替代本轮锁定实例。官方保留文档亦说明可通过 REST 删除不再需要的 trace：[数据保留说明](https://arize.com/docs/phoenix/settings/data-retention)。

目标策略为正文 3 天、每日运行。G0 验证用带合成旧时间戳的过期样本和未过期对照，在公开接口上删除旧窗口，再逐 trace 查询：过期样本不存在，未过期样本仍可查。验证不需要等待真实 3 天，但必须归档目标 3 天／每日调度约定、删除前后读取证据和唯一维护责任。

该 REST 手动验证证明公开清理能力，不证明 M8 的生产每日调度已实现。后续乙须维护调度、游标／窗口、有界批次、失败记录和幂等重试；不得因交接再启动一套 Phoenix 原生定时清理。

## 5. 已排除的原生即时清理假设

官方文档说明 Phoenix 9.0 起支持项目时间／数量保留策略；默认 `0` 天代表无限保留。策略包含规则与 CRON，默认调度可能为每周，所以只设置 `PHOENIX_DEFAULT_RETENTION_POLICY_DAYS=3` 不足以证明每日清理。来源：[官方项目保留策略](https://arize.com/docs/phoenix/settings/data-retention)。

原拟采用“创建新策略后在 150 秒内等待原生清理”的办法已废弃。主代理在固定 Phoenix 21 镜像源码中确认，CRON 分钟字段要求为 0，`TraceDataSweeper` 先等待下一整点；新策略不等于立即执行清理。此处是主代理的锁定源码核对结果，不是研究代理独立运行证明，不应写成 150 秒原生清理通过。

官方 `PATCH /v1/projects/{project_identifier}/retention` 只把项目关联到现有策略，不负责新建策略，也不是立即执行按钮。其 `policy_id:null` 表示恢复默认策略。策略创建／编辑可通过官方 GraphQL 能力进行，但本轮最终选择 REST 时间窗删除后，不再需要为测试编造一个“立即执行原生任务”的 GraphQL mutation。来源：[官方项目路由源码](https://github.com/Arize-ai/phoenix/blob/main/src/phoenix/server/api/routers/v1/projects.py)。

## 6. 证据与尚未完成的验收

本轮研究已核实官方集成、声明兼容范围、认证 bootstrap、默认保留语义及公开清理方向。主代理的独立运行证据负责补齐固定镜像、处理器替换、出口检查、并发关联、脱敏、有界导出故障和实际删除结果；本文不代替这些产物。

- 参数化与对话实际业务入口已经驱动 SDK；外部 SDK 业务交接当前仍待核验。
- 完整 G0 已由总验收负责人确认；独立合成 SDK harness 不替代实际业务路径。
- G1 后端契约冻结、G2 运维 SQL／独立心跳／完整质量统计／告警／五接口、G3 总贯通。
