# 会话短期记忆、审批复苏与长任务规划设计

> 状态：分支能力已实现，2026-11-17 离线合并验收完成；最终行为以本节补充与当前代码为准。验证批次见合并验收记录，实际部署另行验收。
> 本文覆盖三块能力：对话短期记忆、数据管理人工审批的输入框弹窗与状态复苏三要素、
> 出题的规划层与执行层及高压长任务的数量闭环。

## 目标与使用范围

- 短期记忆作用于 `generate`、`creative`、`qa`、`data` 四个对话模式的消息理解环节；
- 审批弹窗作用于 `data` 模式的人工确认交互（前端）；
- 状态复苏三要素作用于 `data` 模式写操作的执行链路（后端）；
- 规划层、执行层与补齐闭环作用于 `generate`、`creative` 的题目生成与对话出题入库链路。

## 短期记忆（系统 Prompt + 最近 3-5 轮对话）

核心模块 [memory.py](../../backend/app/services/rag/memory.py)：

| 构件 | 说明 |
| --- | --- |
| `MEMORY_ROUNDS = 4` | 窗口为 3-5 轮，取 4 轮；一轮 = 一条 user 消息 + 紧随的 assistant 回复 |
| `build_short_term_history(history, rounds)` | 把扁平消息序列解析成轮并取最近 N 轮；开头游离的 assistant 回复丢弃，结尾无回复的 user 消息也算一轮 |
| `build_memory_system(mode, doc_name)` | 系统 Prompt：声明当前模式、文档语境、指代推断与冲突规则（记忆与最新消息冲突时以最新为准） |
| `build_memory_block(...)` | 供必须合并为单个 user prompt 的调用方使用 |

消费方式：

- `chat.py` 的 `send_message`：消息查询扩到 12 条，经 `build_short_term_history` 窗口化后传给技能；
- `slots.extract_slots`：接收窗口化历史，防御性截断后格式化为「短期记忆 · 最近对话轮次」块；
  记忆使用规则（指代推断、沿用已确认槽位、不编造）写入 `SLOT_EXTRACT_SYSTEM`；
- `qa.answer_question`：系统 Prompt = `QA_SYSTEM` + `build_memory_system`，消息携带最近轮次。

异常边界：记忆只用于语境理解，不参与任何持久化；解析失败按空历史处理，不阻断请求。

## 数据管理审批：输入框弹窗与状态复苏三要素

前端（[ChatInput.tsx](../../frontend/src/components/tabs/GenerateTab/ChatInput.tsx)）：
`ConfirmOverlay` 附着在输入框上方（`absolute bottom-full`），替代原对话区 `ConfirmCard`。
弹窗只做简洁说明：`是否确定要删除 N 条XXX？` + 首条影响样本 + 一句话解释，
按钮为「拒绝 / 同意执行」。审批期间分段控制器隐藏，输入禁发（`interactionBusy`）。

后端 [data_agent.py](../../backend/app/services/rag/data_agent.py) 的复苏三要素：

| 要素 | 实现 |
| --- | --- |
| Thread ID | 封印快照存 `thread_id`（= ChatSession.id），执行时强制校验与当前会话一致，跨对话拒绝 |
| 审批意见结果 | `accepted` 在 Lua `GET+DEL` 原子消费封印快照时固定；执行结果与审批意见写回对话消息 |
| State 强制溯源防御 | `target_ids`、`set_name`、`samples` 全部来自封印快照（`sealed_at` 记录封印时间）；执行严禁重跑 DSL 抓取当下数据，快照缺失目标列表的旧格式直接判过期 |

快照写入 Redis（TTL 300s），封存后不可变更。执行时仍按 `user_id` 二次过滤，
防止封印后数据归属变化。异常边界：过期/跨对话/跨账号分别返回 `CONFIRM_EXPIRED`、
`CONFIRM_FORBIDDEN`，不泄露快照内容。

## 规划层与执行层及高压数量闭环

[question_gen.py](../../backend/app/services/rag/question_gen.py)：

- **规划层** `_plan_points`：命题组长角色产出 `count` 个互不重复的细分考点，
  硬性要求考点严格从属于知识点范围；高压（`count >= HIGH_PRESSURE_THRESHOLD=20`）
  时考点输出预算放大到 2400 token，考点不足时按范围细分角度兜底补齐；
- **执行层** `_gen_for_type`：单题并发（`GEN_BATCH_SIZE=1`、6 worker），
  每题绑定计划考点（hint），高压时叠加「主题锁定」硬约束；补齐轮次上限
  `MAX_FILL_ROUNDS=5`；最终数量不足抛 `ValueError`，由 `handle_chat` 转成可读回复。

[chat_flow.py](../../backend/app/services/rag/chat_flow.py) 的 `review_with_refill`：
审核剔除（查重、难度不符、知识错配）后自动进入补齐——按剩余缺口与
`REFILL_BUFFER_RATIO=0.2` 余量重拆题型数量，复用执行层生成（题干跨轮累积去重），
再送审核；轮次上限 `MAX_REFILL_ROUNDS=2`。`chat.py` 用它替换原单次审核，
按各题型缺口接收和补齐，跨轮累计去重及审核统计；有限轮次耗尽后按实际合格数量交付并解释缺口。补齐期间取消传播至原运行的统一回滚与收尾机制，不发布部分批次。

验收标准：要求 50 道行列式计算题时，生成层产出恰 50 道且全部与行列式相关；
审核剔除后自动补齐至 50 道；数量不足时给出明确原因而不是静默少给。

## 接口与数据契约

历史会话列表通过 `GET /api/chat/sessions` 返回当前账号可访问的最近会话，包含会话、题库、文档标识、标题与时间。`GET /api/chat/sessions/{session_id}` 返回消息及持久化的 `mode`（`generate/creative/qa/data`）；前端加载历史后恢复该模式，继续对话不隐式切换或清除原槽位。确认快照为 Redis 内部结构，新增字段对前端透明；聊天回复始终包含 `confirm` 与 `batch_id`，无值时为 `null`。

## 2026-11-17 合并边界与验收

- 前端保留历史侧栏与新建对话，预览清空只删除题目，不删除会话；生成或请求处理中禁止清空，删除成功后更新界面，失败可重试。
- 历史加载期间禁止发送、重试；会话和预览分别校验请求版本，切换、清空或退出后旧响应不回填。
- 闲聊和业务回复统一经过 main 的提交门禁；消息、批次、题目和槽位只在最终事务中发布。闲聊不创建出题台账。
- 审核补齐沿用同一 run，保留原来源模式、创新指令和图片；按每题型缺口补齐，进度统一为 0–100。跨轮题干使用与审核相同的归一化规则，并纳入后续审核语料，不能靠空白或句末标点变化重复交付。
- 审批快照保留删除 `mode` 和会话身份，继续使用一次性消费与执行时归属校验，保留试卷锁和删除门禁；业务变更与确认消息在同一 SQL 事务提交。
- SQL 与 Redis 不构成分布式原子事务；凭据消费后 SQL 失败须重新预览。验收覆盖取消后新运行、混合题型补齐、审批重复确认及 SQL 提交失败。
