## 核心流程

新增代码检查工作流，由 pull request、push 和手动触发。静态检查、后端回归、前端检查与离线回归分别报告结果，任一失败使对应 job 失败，不使用 continue-on-error 或诊断数量基线放行。

Python 使用已锁定的后端依赖及 Phoenix extra，确保当前可选追踪测试执行。Pyright 使用同一虚拟环境与根配置，Ruff 检查 `backend/app`、`backend/tests`。已有类型诊断以明确的类型边界修复，不降低检查级别。

工作流固定使用 Ubuntu 24.04、Python 3.11、Node 22 与 uv 0.12.3。后端以 `pytest -q -n 4 --dist loadfile` 运行，保留 JUnit 报告；前端通过 `npm test` 顺序执行十个离线脚本，截图与结果位于 `.test-results/`，上传时显式包含这个隐藏目录。后端和前端 job 的时限分别为 45 和 20 分钟。后端 job 同时运行 `node --test .github/scripts/verify-release.test.cjs` 验证发布门禁。

前端使用锁文件安装依赖，显式安装受 npm 依赖管理的 Chromium，执行 TypeScript、ESLint、生产构建和统一回归入口。保留真实组件、内存 API、假 Turnstile 与会话隔离断言；浏览器测试不依赖开发者临时目录或 Windows 浏览器版本路径。

## 数据与环境契约

pytest 使用新建临时 SQLite、每测试独立 fakeredis 和模型替身，禁止真实网络。CI 不注入生产 secrets；静态检查需要本地敏感配置模块时仅从占位样例创建，不能读取开发者真实配置。浏览器回归的合成响应不得被描述为真实模型或真实外部服务验收。

旧 G0、真实服务冒烟和需要额外启动隔离台账服务的浏览器联调不混入离线默认入口；保留的专用入口应说明前置条件。

## 异常边界

依赖安装、浏览器安装、子进程超时、断言失败和构建失败均以非零状态结束。测试不得因为缺少浏览器而静默跳过。

## Pages 发布门禁

Pages 仍由 `Deploy to GitHub Pages` 手动触发，仅接受 `main`、`agent` 分支。
本次触发的 `github.sha` 固定为发布版本，流程为 `verify → build → deploy`。
构建显式 checkout 验证通过的 SHA，避免分支随后前进时构建到未经验证的新版本。
部署 job 在环境审批之后、调用 Pages 部署之前再次验证，阻止构建期间新失败或重跑中的检查。
本门禁不会自动发布、回退提交或修改仓库 Rulesets。

`.github/scripts/verify-release.cjs` 通过只读 Actions API 查询同仓库、同分支、同 SHA 的完整运行记录：

| 检查 | 可信工作流与事件 | 必需任务 |
| --- | --- | --- |
| Code checks | `.github/workflows/checks.yml` 的 push 或 workflow_dispatch | 后端 lint/types/tests、前端 lint/types/build/regressions |
| CodeQL Advanced | `.github/workflows/codeql.yml` 的 push 或 workflow_dispatch | actions、javascript-typescript、python 分析 |

先选择最新创建的合格运行，再要求整体和必需任务全部 `completed/success`。
不能用旧成功覆盖新失败或排队中的运行，也不接受其他分支、PR 或其他工作流的成功。
重跑时按每个任务的最新 attempt 判定，允许只重跑失败任务后复用其他任务此前的成功；
完成所有任务检查后重新查询最新运行并集中复核状态，查询期间新增运行、attempt 或结果变化则停止发布。API 无权限、查询异常、记录缺失、任务跳过、
取消、超时或仍在运行均停止发布；完成修复与检查后重新手动触发。

门禁检查的是工作流成功状态，不额外实现 CodeQL 告警级别阈值策略。变更 CodeQL 配置、
工作流路径或必需 job 名称时，须同步更新门禁要求与测试。
各 job 默认只有 contents/actions 读取权限，仅 deploy job 获得 pages 写权限与 OIDC。
Actions API 查询与 Pages 部署不具备原子性；双重校验用于缩小状态变化窗口。

验收使用假 API 回归覆盖上述成功、失败、缺失和竞态情形，并以真实已通过提交进行只读查询验证。
配置验证不触发实际 Pages 部署。手工使用 Actions 选择分支执行发布时，
若 CI 尚未完成，verify 会失败并解释原因；等检查全部通过后重新运行发布工作流。

## CodeQL 扫描与合并策略

`.github/workflows/codeql.yml` 使用 Advanced setup，扫描 main、agent 的 push，以及所有目标为 main 的 PR，另保留手动触发入口。
普通开发分支的单独 push 不运行 CodeQL；Code checks 仍对所有分支的 push 和 PR 运行。
三项矩阵任务分别分析 actions、javascript-typescript、python，使用无构建模式，不安装应用依赖或读取个人配置。
任务权限限定为源码、Actions、包读取与安全扫描结果写入，不使用 pull_request_target。
PR 的 edited 活动也触发扫描，覆盖已有 PR 将目标改为 main 的情况。

仓库默认 CodeQL 设置须关闭，避免与显式工作流冲突。agent 过去为默认扫描添加过传统分支保护；
新工作流在两条长期分支验证成功后已移除该保护，protection API 返回 404；扫描范围由 YAML 决定。
现有独立代码质量 ruleset 保持原配置。

main Ruleset 27438512 要求 GitHub Actions 提供以下全部必需检查：
Analyze (actions)、Analyze (javascript-typescript)、Analyze (python)、CodeQL required。
GitHub 的单项必需检查接受 skipped、neutral，因此 CodeQL required 无条件运行，严格核对三项实际任务均 completed/success，
并核对同 ref、同 SHA、同工作流的三类 CodeQL 分析记录齐全且无处理错误。PR 使用测试合并提交的 SHA 与 refs/pull/.../merge。
另要求 CodeQL 扫描结果阻止错误级别告警和高危及以上安全告警合并。
这些规则仅适用于 main；保留既有 PR、禁止强推和删除规则及其他设置，不添加 bypass。
扫描任务执行成功与安全告警阈值是两项独立条件，不能只凭 Analyze 成功认定不存在阻断告警。

Pages 门禁只认可新工作流在同分支、同 SHA 上的 push 或 workflow_dispatch 结果，不用 PR 扫描替代发布版本扫描。
Default setup 的旧 dynamic 成功记录不能替代新工作流；发布时同样核对三类实际分析记录。工作流必须同步存在于 main 和 agent。
这些校验依赖仓库中的工作流与校验脚本受信任，拥有修改其权限的人仍能改写策略。

## Tag 自动构建部署包

`.github/workflows/release.yml` 响应手动创建的 Tag push，以及 GitHub Release 的 published 事件。
可以在本地 Git 推送标签、使用个人账号的 gh 创建引用，或在 GitHub Releases 页面填写新 Tag 并发布。
Tag 必须使用裸 SemVer 2.0.0：例如 `1.2.3`、`1.2.3-rc.1`、`1.2.3+build.5`；
不接受 `v1.2.3`、`01.2.3`、`1.2.3-01`。校验失败会终止构建，已经创建的 Tag 不会因此自动删除。
不依赖企业版的标签命名规则，不修改用户自行创建的 Tag ruleset。

流程为版本与提交校验 → 复用完整 Code checks → 前端生产构建 → 打包 → 上传 Actions Artifact。
Code checks 继续检查所有分支推送和 PR，并提供 workflow_call 供 Tag 流程复用；普通 Tag push 不再额外启动独立 Code checks。
所有构建使用标签解析后的固定提交。构建前与上传前核对该 SHA 在 main 或 agent 上已有成功的完整 CI 与显式 CodeQL，
任一分支满足即可，其他分支或 PR 结果不能替代。检查缺失、失败、取消、跳过或仍在运行时停止生成发布产物；
等待长期分支检查成功后可重跑失败的构建。不会创建新 Tag、发布 GitHub Release 或部署服务器。

构建产物包含 `mathcraft-{version}.zip` 和 `SHA256SUMS`。
ZIP 内顶层目录为 `mathcraft-{version}/`，包含已提交的后端运行源码、Alembic 迁移、依赖声明与锁文件、
前端 `frontend/dist/`、部署说明 `DEPLOY.md` 及文件哈希清单 `release.json`。
这是需要在服务器安装依赖的完整应用部署包，不包含 Python 运行时、已安装依赖、真实密钥、数据库、用户上传或索引。
部署依照包内 DEPLOY.md 配置外置数据与凭据、Redis、数据库迁移、后端服务和前端反向代理。

后端只从固定 Git 提交读取白名单文件，前端只接收本次构建的 dist，拒绝符号链接、路径越界、敏感配置和运行时文件。

验收包括 SemVer 边界、ZIP 内容与清单、提交一致性、敏感路径排除及工作流静态校验；
