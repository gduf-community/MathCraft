## 目标与范围

清理已失效的手工测试入口，将当前应用的静态检查和可重复运行的回归接入 GitHub Actions。保留认证、授权、事务、迁移、检索与恢复测试，不以删除失败测试代替修复。

## 核心流程

新增代码检查工作流，由 pull request、push 和手动触发。静态检查、后端回归、前端检查与离线回归分别报告结果，任一失败使对应 job 失败，不使用 continue-on-error 或诊断数量基线放行。

Python 使用已锁定的后端依赖及 Phoenix extra，确保当前可选追踪测试执行。Pyright 使用同一虚拟环境与根配置，Ruff 检查 `backend/app`、`backend/tests`。已有类型诊断以明确的类型边界修复，不降低检查级别。

工作流固定使用 Ubuntu 24.04、Python 3.11、Node 22 与 uv 0.12.3。后端以 `pytest -q -n 4 --dist loadfile` 运行，保留 JUnit 报告；前端通过 `npm test` 顺序执行十个离线脚本，截图与结果位于 `.test-results/`，上传时显式包含这个隐藏目录。后端和前端 job 的时限分别为 45 和 20 分钟。后端 job 同时运行 `node --test .github/scripts/verify-release.test.cjs` 验证发布门禁。

前端使用锁文件安装依赖，显式安装受 npm 依赖管理的 Chromium，执行 TypeScript、ESLint、生产构建和统一回归入口。保留真实组件、内存 API、假 Turnstile 与会话隔离断言；浏览器测试不依赖开发者临时目录或 Windows 浏览器版本路径。

## 数据与环境契约

pytest 使用新建临时 SQLite、每测试独立 fakeredis 和模型替身，禁止真实网络。CI 不注入生产 secrets；静态检查需要本地敏感配置模块时仅从占位样例创建，不能读取开发者真实配置。浏览器回归的合成响应不得被描述为真实模型或真实外部服务验收。

旧 G0、真实服务冒烟和需要额外启动隔离台账服务的浏览器联调不混入离线默认入口；保留的专用入口应说明前置条件。

## 异常边界

依赖安装、浏览器安装、子进程超时、断言失败和构建失败均以非零状态结束。测试不得因为缺少浏览器而静默跳过。

## Pages 发布门禁

Pages 仍由 `Deploy to GitHub Pages` 手动触发，仅接受 `main`、`agent` 分支。
本次触发的 `github.sha` 固定为发布版本，流程为 `verify → build → deploy`。
构建显式 checkout 验证通过的 SHA，避免分支随后前进时构建到未经验证的新版本。
部署 job 在环境审批之后、调用 Pages 部署之前再次验证，阻止构建期间新失败或重跑中的检查。
本门禁不会自动发布、回退提交或修改仓库 Rulesets。

`.github/scripts/verify-release.cjs` 通过只读 Actions API 查询同仓库、同分支、同 SHA 的完整运行记录：

| 检查 | 可信工作流与事件 | 必需任务 |
| --- | --- | --- |
| Code checks | `.github/workflows/checks.yml` 的 push 或 workflow_dispatch | 后端 lint/types/tests、前端 lint/types/build/regressions |
| CodeQL 默认设置 | `dynamic/github-code-scanning/codeql` 的 dynamic | actions、javascript-typescript、python 分析 |

先选择最新创建的合格运行，再要求整体和必需任务全部 `completed/success`。
不能用旧成功覆盖新失败或排队中的运行，也不接受其他分支、PR 或其他工作流的成功。
重跑时按每个任务的最新 attempt 判定，允许只重跑失败任务后复用其他任务此前的成功；
完成所有任务检查后重新查询最新运行并集中复核状态，查询期间新增运行、attempt 或结果变化则停止发布。API 无权限、查询异常、记录缺失、任务跳过、
取消、超时或仍在运行均停止发布；完成修复与检查后重新手动触发。

门禁检查的是工作流成功状态，不额外实现 CodeQL 告警级别阈值策略。变更 CodeQL 配置、
工作流路径或必需 job 名称时，须同步更新门禁要求与测试。
各 job 默认只有 contents/actions 读取权限，仅 deploy job 获得 pages 写权限与 OIDC。
Actions API 查询与 Pages 部署不具备原子性；双重校验用于缩小状态变化窗口。

验收使用假 API 回归覆盖上述成功、失败、缺失和竞态情形，并以真实已通过提交进行只读查询验证。
配置验证不触发实际 Pages 部署。手工使用 Actions 选择分支执行发布时，
若 CI 尚未完成，verify 会失败并解释原因；等检查全部通过后重新运行发布工作流。
