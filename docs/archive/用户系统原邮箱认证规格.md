- `frontend/src/store/AuthContext.tsx` 把 token 持久化在 localStorage；`frontend/src/api/backend.ts` 集中添加 Bearer 头；这些是明确迁移点。

- 当前无注册、邮件验证码、密码恢复、Turnstile、JWT 刷新接口。以上是静态核查；未读取真实环境文件或数据库，未验证本机账号能否登录。

## 历史记录｜3. 页面与主流程

### 历史记录｜3.1 登录页

本节是原分支的两种登录方案；当前另有“开通账号登录”，并保留教师/学生身份选择用于邮箱码和学工号登录。

保留教师/学生身份入口；认证方式分为“邮箱验证码”“学工号密码”，不额外开放传统用户名或手机密码登录。服务端根据账号实际角色校验所选身份，前端角色不能授予权限。

邮箱登录：填写邮箱 → Turnstile → 发码 → 填验证码 → 登录成功进入工作台。不存在的邮箱发码阶段返回统一受理信息，不发真实邮件；验证码提交时不建号，以通用失败提示提供注册入口，避免增加直接的账号枚举接口。

学工号登录：填写学工号、密码 → Turnstile → 服务端校验 → 建立会话。失败保留输入，仅重置已消费或过期的人机验证 token；密码只保存在组件内存。

### 历史记录｜3.2 注册页

邮箱、验证码、显示名称、教师/学生身份、密码及确认密码必填；学工号选填。先做人机验证和发送注册专用验证码，最后一次提交完成字段校验与邮箱验证。原稿曾仅要求前端确认密码；此点已由实现替代：后端同时接收 password 与 confirm_password，独立校验密码策略及两次一致性。

账号和个人模型设置在同一数据库事务创建；邮箱验证与学工号唯一冲突返回可处理错误，不能留下半个用户。注册成功返回访问令牌、用户信息并设置刷新 Cookie，直接进入工作台。

并发注册通过唯一索引兜底，不依赖“先查询不存在”；注册已提交但刷新会话生成失败时，明确返回“账号已创建，请登录”，不假报注册回滚，不自动重试创建账号。

### 历史记录｜3.3 忘记密码

填写邮箱 → Turnstile → 发送 reset_password 验证码 → 提交验证码、新密码、确认密码 → 更新密码并撤销全部会话 → 返回登录页。

验证码错误、过期、网络错误均保留新密码及确认密码；成功、用户离开表单或主动清空时销毁内存值。禁用账号不能借重置恢复 active。未注册邮箱不创建用户。

### 历史记录｜3.4 个人中心

- 普通资料：显示名、学校等沿用现有入口；禁止通用 PATCH/PUT 直接修改 email、user_no、role、密码或认证状态。
- 修改密码：登录态＋当前密码＋新密码；成功撤销所有会话，回登录页。
- 更换邮箱：已登录 → 建立绑定当前用户及当前邮箱的换绑事务 → 分别通过人机验证向旧、新邮箱发专用码 → 提交两个 proof 与新邮箱 → 原子换绑并撤销全部会话。
- 新邮箱必须未被其他账号占用；提交时再验唯一性与旧邮箱快照；不能拿注册码或另一换绑事务的码替代。
- 学工号：已登录＋当前密码；允许添加、更换、移除。唯一性提交时兜底；验证密码与更新之间校验凭据版本，避免并发改密后沿用旧验证。原有角色、主键和业务关联不变。
- 旧邮箱不可访问时无绕过验证入口，明确提示本期限制。

## 历史记录｜4. 认证与持久化设计建议

### 历史记录｜4.1 用户数据与登录标识

角色仅 teacher/student、account 不可输入的范围仅适用于原邮箱分支；当前 UserPayload 包含 admin，无邮箱账号使用 account 登录。

保留不可变 users.id 作为资源归属主键。保留历史 account 字段以兼容已有引用，新用户内部生成不可输入登录的 account，不用邮箱或学工号替代主键。

新用户增加 email_verified_at、auth_version。role 仅 teacher/student，identity 由 role 派生；新增约束前检查历史异常值。user_no 继续可空、唯一；移除写 NULL，不写空字符串。手机号可留作非认证资料，但退出登录标识范围。

邮箱去首尾空白、校验格式；域名小写并按明确规范存储。建议产品层把邮箱登录视为不区分大小写，迁移时先扫描大小写冲突，不静默合并用户；不移除加号标签或点号等提供商特性。学工号去首尾空白，保留前导零，禁止控制字符；初版保持大小写敏感，表单提示明确。

密码建议 8–64 字符，另校验 UTF-8 编码不超过 bcrypt 的 72 字节边界；禁止静默截断。继续校验已有 bcrypt 哈希，存储时不记录明文，不把 8 字符新策略作为旧账号登录拦截条件。验证码错误与密码错误都不输出请求秘密。

### 历史记录｜4.2 JWT 与立即撤销

建议访问 JWT 有效期 15 分钟，固定 HS256 算法、至少 32 随机字节签名密钥；部署可配置，不提供硬编码缺省密钥。仅使用成熟 JWT 库，不手写签名。固定校验签名算法、iss、aud、sub、exp、iat、令牌类型，以及可选 nbf；不能信任请求头指定其他算法。

claims 包含 sub、sid、auth_version、jti、iat、exp、iss、aud；不装载密码、邮件码、模型密钥或个人资料。权限从数据库用户与资源关系读取，不信任 JWT 内角色快照。

引入 auth_sessions 表保存 sid、user_id、创建时 auth_version、状态、创建/到期时间和刷新令牌摘要。每次受保护请求同时校验 JWT、用户 active、auth_version 和对应会话有效性。因此退出、改密与换绑立即影响尚未到期 JWT，而不是等待 15 分钟。

改密、重置、换绑在同一数据库事务更新数据、递增 auth_version 并撤销会话；不依赖提交后再清 Redis 才保证安全。后续按该方案修改禁用流程；auth_version 不因重新启用回退，旧会话不能复活。授权会话状态存储不可用时拒绝认证，不降级为只验 JWT。

并发边界：登录、发放新会话与刷新必须把校验得到的 auth_version 作为事务内条件再次核对，并与改密/换绑采用同一串行化或条件更新策略；不能在旧密码验证后读取新版本并据此签发有效会话。全设备撤销保证提交后新进入的认证检查拒绝旧凭据，不能撤回已经执行的业务操作；敏感写操作在提交事务中再次核对认证版本。具体数据库实现须以当前 SQLite 的并发行为验证，不假设其支持行级 FOR UPDATE。

刷新令牌使用高熵随机不透明值，而非第二个访问 JWT；服务端只存摘要。建议绝对最长 7 天，无无限滑动延期；每次刷新原子轮换，已消费旧值记录至到期，用于识别重放并撤销该会话族。普通登出只撤销 sid，全部撤销依赖用户版本。

同浏览器并发请求统一 single-flight 刷新，多标签通过浏览器锁或协调通道串行刷新；明确复用旧刷新令牌会撤销该会话，响应丢失时可能需要重新登录，不以无限重试或长期复用旧值掩盖风险。

### 历史记录｜4.3 浏览器存储与 CSRF

访问令牌仅存在内存；刷新令牌用 HttpOnly Cookie，生产 Secure、SameSite=Lax、Path=/api/auth，无 Domain。页面刷新调用 refresh 再取 me，不继续读取旧 localStorage token。

Cookie 认证的 refresh/logout 请求必须检查可信 Origin、JSON Content-Type 和 CSRF 防护头/令牌；绑定精确 CORS 来源，不能用带凭据的通配符。若未来跨站部署需单独评审 SameSite=None/CSRF，不偷偷放开。普通业务 API 仍使用 Bearer。

客户端对 token 过期最多刷新并重试原请求一次；仅在认证层确认未执行的请求允许重试，非幂等业务操作不盲目重放。初始恢复显示 loading，避免登录页闪现；刷新失败清内存与 Cookie 并回登录页。

## 历史记录｜5. 邮件验证码与 SMTP

当前公开 register/login/reset_password 发码均为响应后投递、统一 202；仅换绑发码同步失败返回 503。Redis 校验状态与 SQL AuthProof 唯一消费共同工作，不存在跨存储原子提交。

建议验证码为随机 6 位数字、5 分钟有效、最多错误 5 次；每邮箱每用途 60 秒内最多一次、每小时最多 5 次，每来源 IP 每小时最多 30 次。均为建议初值，可配置，按实际内部使用评估。

用途分别为 register、login、reset_password、email_change_old、email_change_new，严格绑定规范化邮箱；换绑另绑定 user_id、change_id、旧/新邮箱快照。发码返回不可预测 challenge_id；验码必须同时提交 challenge_id 和用途绑定，不能只按邮箱查码。

Redis 保存验证码的服务端 HMAC 摘要、到期、次数、状态；HMAC 密钥独立于 JWT 密钥。原子校验、扣减次数与消费，错误不立即删除，超过次数锁定。重新发送使旧 challenge 失效；并发发码原子控制频率，不能竞争出两份有效码。

跨 Redis/SQL 无分布式事务：以短期 proof/reservation 防并发消费，数据库事务内记录 proof 唯一消费或等效幂等凭证，成功后完成 Redis 消费；不得声称两个独立提交是原子操作。密码重置及换绑 proof 绑定 auth_version，事务提交前再次核对，防并发安全操作覆盖。

SMTP：生产 TLS/STARTTLS、认证与超时明确配置。密码不进入日志。发送失败不留下可提交的有效 challenge；限流失败计数不因邮件失败自动清零。可用性响应不泄露注册状态；服务商错误映射为脱敏业务错误。

换绑用途的发码必须有有效登录态，且服务端从 change_id 解析对应用户和邮箱，不接受客户端任意指定收件人。未注册邮箱的登录/重置发码使用不泄露存在性的统一响应，不发送有效登录/重置码，也不自动建号；登录页始终提供注册入口，最终失败使用通用提示。注册邮箱已占用的提示与限流需在实施时核对枚举风险。

验证码不放 URL、响应或日志。单元/集成测试注入内存假发件箱；开发假邮件模式只能显式开发环境使用，不能通过公开 API 泄露任意用户验证码。忘记密码与登录各用独立用途，验证码不可互换。

## 历史记录｜6. Turnstile 集成

前端嵌入官方组件，后端调用 Siteverify 验 token，检查 success、预期 hostname 和 action。发码 action 为 email_code，密码登录为 password_login；服务端按路由固定预期，不由客户端指定并信任。

Cloudflare 官方规定 token 五分钟有效且单次使用；失败、过期、重复、网络异常需重置组件取新 token。服务端请求有超时，安全重试复用同一个 Siteverify idempotency_key，不把已验证 token 用于多个业务操作。

注册、重置与换绑的发码请求都经过 Turnstile；验证码提交另有限流和次数校验，不强制每次输码再次挑战。人机验证不替代密码/邮件归属验证或权限校验。

- 开发：官方测试 Site Key/Secret 成对配置，可测试成功、失败和重复；自动化测试使用假 Siteverify，不访问 Cloudflare。
- 生产：缺真实密钥、域名白名单，或检测到官方测试密钥则启动校验失败/认证入口明确不可用，不静默绕过；外部异常按拒绝处理。
- 部署配置核心是网站 hostname；访问者 remoteip 是 Siteverify 可选参数，不是服务器 IP 注册门槛。只信任已配置反向代理提供的客户端地址，不直接相信任意 X-Forwarded-For。
- Widget Site Key 可公开，Secret 仅后端；不需要将网站接入 Cloudflare 代理或本期额外配置 Access/WAF 门控。

### 历史记录｜PR #8 修复后的契约边界（2026-11-05）

退出不再以浏览器共享 Cookie 选定会话：必须携带本标签签名有效的 Bearer，后端撤销其中 sid，仅同会话 Cookie 会被清除。注销独有地允许 access 已过期；业务认证仍拒绝到期令牌。Origin、JSON 与双提交 CSRF 校验保持，缺本地 access 时前端只清本地，不匿名注销其他账号。上传仅对显式 `ACCESS_TOKEN_EXPIRED` 重试一次，撤销、角色／账号切换和旧响应不能重放或回填。【当时边界，注册项已替代】当时登录／重置发码统一 202、注册／换绑失败 503；当前注册也统一 202，只有换绑发码同步失败 503。离线审计与 HTTP 共用 `app.auth_validators`，拒绝相同非法标识；响应模型及 422 脱敏结构、Cookie/CSRF/Bearer 输入完整进入 OpenAPI。

发码隐私补充：登录和密码重置先返回统一 202，再在响应后发送邮件；SMTP 成功、慢响应或超时均不改变已返回结构。只有成功投递的最新验证码可验证，进程中断可能丢失未完成投递，冷却后可重发。退出撤销失败时登录页提供“重试退出”，原凭证仅在当前页面内存中用于撤销，禁止刷新恢复。

## 来源二：用户系统实施规格中的历史方案

## 历史记录｜Problem Statement

个人教师和学生需要独立注册、可靠登录和自行恢复账号，而不依赖管理员开通。当前系统已有用户及资源归属，但缺少自助注册、邮箱验证码、完整密码恢复、人机验证和可立即撤销的 JWT 会话；旧登录标识混用、资料直改邮箱和撤销会话的失败窗口也需要一并消除。开发者需要可配置的教师、学生默认账号，以降低本地联调成本，同时不能向生产引入默认密码或认证旁路。

## 历史记录｜Solution

提供邮箱验证注册、邮箱验证码登录及学工号密码登录。注册后自动进入对应工作台；用户可在个人中心安全维护学工号、密码和绑定邮箱。所有发码和密码登录接入 Turnstile，使用短期 JWT 与可撤销刷新会话。开发账号通过后端环境配置及显式初始化命令创建，开发快捷按钮只填充、不自动登录。保持现有用户 ID、角色权限和数据归属不变。

## 历史记录｜User Stories

1. 作为个人教师，我希望无需邀请或管理员审批即可注册，以便独立使用服务。
2. 作为学生，我希望选择学生身份注册，以便进入自己的工作台。
3. 作为注册者，我希望验证邮箱归属，以便后续使用邮箱登录及恢复密码。
4. 作为注册者，我希望填写显示名称、密码和确认密码，以便建立完整账号。
5. 作为注册者，我希望不填写学工号、学校或手机也能完成注册，以便先使用服务。
6. 作为注册者，我希望不再额外创建用户名，以便减少重复填写。
7. 作为注册者，我希望注册成功立即登录并进入对应工作台，以便无需再次完善资料。
8. 作为用户，我希望用邮箱验证码登录，以便未绑定学工号也能访问账号。
9. 作为用户，我希望用学工号和密码登录，以便沿用日常编号。
10. 作为未注册访问者，我希望看到独立注册入口，以便明确完成注册而非被自动建号。
11. 作为用户，我希望身份或密码不匹配时拒绝登录，以便保护角色边界。
12. 作为用户，我希望验证码过期、错误、次数耗尽或发送过频时收到可理解的提示，以便正确重试。
13. 作为用户，我希望重发验证码后旧码失效，以便只使用最新邮件。
14. 作为忘记密码的用户，我希望通过绑定邮箱重置密码，以便自行恢复访问。
15. 作为重置密码的用户，我希望验证码填错时保留已输入的新密码与确认密码，以便无需重复填写。
16. 作为重置密码的用户，我希望重置成功后全部设备下线并返回登录页，以便旧凭据失效。
17. 作为已登录用户，我希望验证当前密码后修改密码，以便保护账号。
18. 作为用户，我希望更换邮箱时验证旧、新邮箱，以便防止未经授权的换绑。
19. 作为用户，我希望换绑成功后全部设备重新登录，以便旧邮箱和旧会话不再访问账号。
20. 作为用户，我希望能在个人中心添加、修改和移除学工号，以便维护登录标识。
21. 作为用户，我希望学工号变更需要当前密码且冲突时不覆盖他人，以便保持标识安全唯一。
22. 作为用户，我希望未绑定或移除学工号后仍可邮箱登录，以便不会被锁在账号外。
23. 作为用户，我希望可同时登录多个设备，以便跨设备使用。
24. 作为用户，我希望普通退出仅撤销当前设备，以便不干扰其他设备。
25. 作为用户，我希望页面刷新和访问令牌过期时安全续期，以便减少重复登录。
26. 作为用户，我希望认证服务异常时不会绕过校验，以便故障不降低安全性。
27. 作为已有用户，我希望升级后保留题库、试卷、收藏及个人配置归属，以便不丢失历史数据。
28. 作为开发者，我希望在后端 .env 配置默认教师和学生账号，以便灵活联调。
29. 作为开发者，我希望显式初始化可重复执行且不重置已有密码或角色，以便保护本地数据。
30. 作为开发者，我希望教师和学生按钮仅填充对应账号并手动登录，以便仍验证正常认证流程。
31. 作为部署者，我希望生产禁止默认账号初始化和开发凭据接口，以便不暴露开发能力。
32. 作为部署者，我希望 SMTP、JWT 和 Turnstile 从部署配置读取并严格校验，以便不提交真实凭据。

## 历史记录｜Implementation Decisions

### 历史记录｜领域与模块边界

“无管理员角色”和内部 account 不可输入是原邮箱分支范围；当前三角色及账号登录契约见上文。

- 在既有认证、用户资料、数据模型、配置、邮件服务和前端认证状态边界内扩展；路由负责编排，验证码、会话和人机校验使用内聚服务，不创建平行用户系统。
- 注册仅需邮箱、验证码、显示名称、密码、确认密码和教师/学生身份；学工号可空。单账号单身份，初版不可切换，无管理员角色。
- 保留不可变用户 ID；历史内部 account 不再是可输入登录标识，新用户内部生成。identity 从 role 派生，历史不一致必须先报告处理。
- 邮箱去首尾空白，按不区分大小写的登录策略建立规范化与唯一约束；不合并点号或加号标签。学工号去首尾空白、保留前导零、大小写敏感、全平台唯一，移除存 NULL。数据库约束处理并发竞争，不仅预查询。
- 新密码为 8–64 字符，且 UTF-8 不超过 bcrypt 72 字节，不静默截断；兼容既有哈希，不因新长度策略拒绝旧密码登录。

### 历史记录｜流程与对外契约

本节“不支持历史用户名登录”针对已移除的通用 OR 查询旁路；当前另有受限无邮箱 /login/account，不恢复旧旁路。

- 分离邮箱验证码和学工号密码登录，均校验教师/学生身份；不支持邮箱密码、手机或历史用户名登录，不保留可绕过新流程的通用旧入口。
- 拟议契约：GET /api/auth/config；POST /api/auth/email-code、/register、/login/email、/login/password、/refresh、/logout、/password/reset；GET /api/auth/me；PUT /api/auth/password。
- 安全资料契约：POST /api/users/me/email-change；PUT /api/users/me/email、/user-no。普通资料更新不得直接改邮箱、学工号、角色、密码或认证状态。
- 用户与初始模型设置同事务创建；若账号已提交但会话创建失败，明确提示“账号已创建，请登录”，不假报注册已回滚，不重复建号。正常注册成功返回当前用户、短期 access token 和刷新 Cookie；注册自动登录。密码重置、修改密码、换绑邮箱成功后撤销全部会话并返回登录，不自动创建新会话。
- 换绑事务绑定用户、旧/新邮箱快照和认证版本，有效 10 分钟；发码必须有有效登录态，收件人由事务解析。旧、新邮箱各自的验证码都通过才原子提交；旧邮箱不可访问不提供绕过或申诉入口。
- 学工号增改删验证当前密码；标识冲突或密码错误不修改数据；提交时再次校验认证版本，不能沿用并发改密前的密码验证结果，不改变用户 ID、身份与资源归属。显示名称去空白后不得为空。
- 未注册邮箱登录与重置不建号，发码响应避免泄露账号是否存在；登录页始终提供注册入口。业务错误结构一致，限流 429 加 Retry-After，依赖不可用 503；不返回秘密或堆栈。
- 前端明确 loading、失败、成功及禁用状态；错误或过期验证码及网络失败保留新密码/确认密码于组件内存，成功、离开或主动清空时销毁，不持久化。

### 历史记录｜验证码、SMTP 与人机验证

- 邮件码为随机 6 位数字、5 分钟有效、最多错误 5 次；每邮箱每用途重发间隔 60 秒、每小时最多 5 次，每来源 IP 每小时最多 30 次，均可配置。
- 分离注册、登录、重置、旧邮箱换绑及新邮箱换绑用途；challenge 绑定规范化邮箱、用途及必要的变更事务/认证版本；不可预测 ID，重发旧 challenge 失效。
- Redis 保存独立密钥 HMAC 摘要与状态，原子控制尝试和消费；涉及 SQL 的操作通过唯一消费凭证及事务版本条件防止并发重复执行，并定义提交失败与重试恢复，不把两个存储的独立提交误认为原子事务。
- SMTP 明确 TLS/STARTTLS、认证和超时；失败不遗留有效可消费码，也不清零滥用限流。日志不输出密码、验证码、Cookie 或令牌。测试用假发件箱。
- 所有邮箱发码及学工号密码登录执行 Turnstile 前端挑战和服务端 Siteverify，固定核验 hostname/action。过期、重复、失败与网络异常不得放行，重试需新挑战或同一 Siteverify 幂等键。
- 开发可配官方测试密钥，自动化使用假验证服务；生产缺真实配置、误用测试配置或外部服务不可用时拒绝认证入口。上线按 hostname 配置，不等待服务器 IP 才开始实现；可信代理配置控制来源 IP，不信任任意转发头。

### 历史记录｜JWT、刷新与即时撤销

当前退出必须绑定本标签 Bearer 的 sid；只有同 sid Cookie 被清除，不能把“幂等清 Cookie”解释为清除另一账号或设备的共享 Cookie。

- 访问 JWT 15 分钟，固定 HS256，签名密钥至少 32 随机字节；使用成熟库，校验固定算法、签名、iss/aud、sub/sid、类型、iat/exp、认证版本和会话状态。
- 数据库持久化设备会话和用户认证版本；每次认证查询用户 active、版本及会话有效性，权限以当前用户与资源关系为准，不依赖角色快照。
- 修改密码、重置与换绑在同一事务修改数据、增加认证版本并撤销会话。登录和刷新以原校验版本作事务条件，防旧密码校验后签发新版本会话；以 SQLite 实际并发语义验证。
- 撤销提交后新进入的认证检查必须拒绝旧 JWT；敏感写入在事务提交前再次核验版本。已执行操作无法回撤；状态存储故障不退化为仅验签名。
- 高熵不透明刷新令牌仅存摘要，绝对最长 7 天，每次原子轮换，保留旧摘要以识别重放并撤销对应会话族。普通退出仅撤销当前 sid，幂等清 Cookie，不接受任意他人 sid。
- 访问令牌只存内存；刷新 Cookie 为 HttpOnly、生产 Secure、SameSite=Lax、Path=/api/auth，无 Domain。刷新/退出校验精确 Origin、CSRF 及 JSON 请求边界，CORS 不允许凭据通配来源。
- 页面恢复用刷新 Cookie 获取 access token，再读取用户。单标签刷新单飞，多标签协调；业务请求仅在认证确认未执行时最多刷新重试一次，不盲目重放非幂等操作。刷新终止失败清状态，响应丢失可能要求重新登录。

### 历史记录｜开发账号与迁移

- 后端 .env 配置显式开发开关及教师、学生各自邮箱、学工号、密码和显示名称；配置名及生产校验纳入样例，实际文件不入库。
- 显式开发初始化在写入前校验环境与完整配置；可创建已验证的开发邮箱，生产拒绝。幂等只跳过确定同一预期账号；冲突、角色不符报错，绝不覆盖、合并、重置或输出密码。
- 开发按钮只填充身份/学工号/密码，仍手动提交并走 Turnstile 与真实认证。仅受控本机开发、显式开关允许专用 no-store 填充端点；前后端都只绑定回环地址，精确 Origin，禁止共享入口/外部代理，生产不挂载，不把密码编入前端产物。
- 迁移先增加可兼容字段，再检查缺邮箱、未验证邮箱、标识大小写冲突及角色异常；不自动认证历史邮箱、不猜测、不静默合并。发布前由数据拥有者按受控迁移清单补齐，无法安全补齐则阻断发布。
- 保留资源外键与用户 ID；切换后拒绝旧 mc_ token 并清旧浏览器存储；删除旧登录和公开旧密码改密旁路。真实数据迁移前备份，不在本规格阶段读取数据库或执行迁移。
- 实现时同步真实 OpenAPI、生成接口文档、前端类型、启动与配置说明；此规格不提前改写当前运行契约。

### 历史记录｜生产认证密钥生成与配置交付（2026-11-05）

- 目标与范围：为部署者提供手工生成应用认证秘密值的独立入口及完整配置说明；不扩展认证 API、第三方服务开通、数据库迁移或上线能力。字段、默认值和来源以当前 `backend/app/config.py`、`backend/.env.example` 为准，配置与初始化入口见 [后端 README](../../backend/README.md#2-安装依赖与初始化配置)，本地启动步骤见 [根 README](../../README.md#启动方法)。
- 核心流程与秘密交付契约：由部署平台的秘密管理服务或经批准的密码管理器独立生成 JWT 与验证码密钥，各至少 32 字节，建议 48 随机字节；经受控秘密注入配置。仓库不提供 stdout 密钥生成器，不加载应用或接入真实服务来生成秘密值。
- 保存与异常边界：既有 `backend/.env` 只编辑同名字段，不整份覆盖，不将命令输出重定向到配置，不提交或在终端/共享日志/聊天展示秘密值，并限制部署账号访问。SMTP 与 Cloudflare Turnstile 凭据从各自供应商获取；缺配置或依赖故障保持拒绝边界。
- 生产约束：显式设置 `APP_ENV=production`、`DEV_ACCOUNTS_ENABLED=false`，清空 `DEV_TEACHER_EMAIL`、`DEV_TEACHER_USER_NO`、`DEV_TEACHER_PASSWORD`、`DEV_TEACHER_DISPLAY_NAME`、`DEV_STUDENT_EMAIL`、`DEV_STUDENT_USER_NO`、`DEV_STUDENT_PASSWORD`、`DEV_STUDENT_DISPLAY_NAME` 八个字段。JWT issuer/audience、访问/刷新有效期、邮件码有效期/错误次数/重发/邮箱及 IP 限额、全部 SMTP/Turnstile 字段按根清单配置。CORS 使用精确 HTTPS Origin（含协议及必要端口、无路径）；Turnstile hostname 仅主机名（无协议、端口、路径），与 widget 配置一致。代码默认 `APP_ENV=production` 与模板的 `development` 区别必须说明，不将本机样例冒充生产值。
- 持久化边界：SQLite 相对数据库路径按进程工作目录解析，四项存储目录的相对路径按 `backend/` 解析；生产配置受控数据库/Redis 和源码外持久卷绝对路径并安排备份、迁移。保留用户 ID、资源及 `UserModelSetting` 归属，个人模型设置仍经 `/api/users/me/model-settings` 管理，不能把生成认证密钥等同于配置模型服务。
- 轮换边界：同一部署全部进程与实例共用同一组密钥及 issuer/audience，不每次启动再生。轮换 JWT 密钥影响旧访问 JWT，轮换邮件码密钥影响旧验证码；数据库刷新会话按摘要、状态和认证版本管理，换 JWT 密钥本身不必然撤销 refresh。若需撤销既有会话，使用现有会话撤销流程，并协调所有实例更新配置与重启。
- 验收标准：不存在明文 stdout 认证密钥生成入口；根目录树与实际文件一致，配置文档与样例覆盖字段、默认值、来源及上述边界，本地链接有效。仅核对静态差异与链接，不接入真实凭据、SMTP/Cloudflare、数据库或 Redis，不据此宣称上线验收完成。

## 历史记录｜Testing Decisions

- 沿用已接受设计中的验收方案：主接缝为现有 HTTP API 测试客户端，覆盖从注册/登录到受保护资源访问的外部行为；参考既有认证与资料接口测试，不绑定私有函数结构。
- SMTP 和 Siteverify 使用依赖注入假服务，时间与随机性可控；使用临时数据库和逐测试独立 fakeredis（含 Lua），不连接或清空本机 Redis，禁止接入未知 Redis、真实邮箱或 Cloudflare。
- 必测注册成功/缺学工号/邮箱及学工号并发冲突、两种登录、身份不匹配、未注册不建号、禁用用户和资源隔离不退化。
- 必测验证码用途/邮箱/事务绑定、到期、错误次数、重发、并发消费、SMTP 失败及 SQL 提交失败后的恢复；安全操作失败不产生部分变更。
- 必测旧/新邮箱双验证、普通资料接口无法绕过、学工号密码验证、版本竞争、并发登录/刷新与全设备撤销；退出当前设备不影响其他设备。
- 必测 JWT 错算法/签名/iss/aud/时间/用户/版本/会话、刷新重放和轮换、Cookie 属性及 CSRF/Origin；依赖故障 fail closed。
- 并发验收以可重复调度的真实 SQLite 事务竞争为证据，不用串行 mock 替代；在既有客户端/服务依赖替换点注入 SMTP、Siteverify、时钟及 Redis/SQL 故障，仅在现有接缝不足时新增最小适配层。
- 浏览器级验证注册直达工作台、页面恢复、并发/多标签刷新、重置成功返回登录、验证码错误保留两个密码输入。断言用户可观察行为，而非组件实现快照。
- 显式初始化通过命令级测试验证环境拒绝、幂等、跨账号冲突与不输出密码；迁移用合成历史数据验证用户 ID/归属保留及异常阻断；生产构建确认无开发凭据和开发端点。
- 实现后运行相关后端测试及认证/隔离全量测试、Ruff、适用 Pyright、前端 typecheck/lint，以及认证路由/生产构建相关 build。仅文档阶段检查差异、引用和覆盖，不运行数据库或 Redis 测试。
